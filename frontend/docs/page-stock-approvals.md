# 入库审批与出库审批页面实施设计

本文定义 `/approvals/inbound`“入库审批”和 `/approvals/outbound`“出库审批”的前端实施方案。两页使用同一套审批队列、审核详情、确认操作、异步状态和响应式结构，仅通过领域配置表达入库与出库的真实业务差异。

当前状态：两个审批路由已替换为正式共享工作台，完成 pending 队列、关键词与日期筛选、触底追加、按需详情、单据内确认、通过/拒绝、组合权限、并发错误处理和响应式布局。core 已提供 pending 单据查询、单据详情和四个审批动作接口，因此本页没有新增审批 CRUD，也没有复制入库单、出库单历史查询页的完整实现。

通用视觉、页面骨架、三段式列表、浮层、异步反馈和量化验收以 `visual-style.md`、`ui-design-guidelines.md`、`ui-consistency-checklist.md` 和 `async-state-transitions.md` 为准。本文只补充库存审批业务的功能、界面和共享边界。

## 结论

实现一个共享“库存审批工作台”，由两个薄路由页分别注入入库和出库配置：

```text
InboundApprovalsPage.vue  ─┐
                           ├─ StockApprovalWorkspace.vue
OutboundApprovalsPage.vue ─┘   ├─ ApprovalQueueList.vue
                               ├─ ApprovalReviewDialog.vue
                               └─ ApprovalActionConfirmation.vue
```

- 两页共享查询、搜索、日期筛选、触底追加、详情加载、通过、拒绝、并发保护和成功后队列衔接。
- 业务配置只定义标题、权限、API 方法、字段标签、库存影响文案、明细渲染器和错误映射。
- 不创建两份近似页面、近似 SCSS、状态标签或确认逻辑。
- 不把审批按钮放回 `/inbound/orders` 或 `/outbound/orders`；历史查询页只负责查看并跳转到对应审批路由。

## 当前项目现状

### 已具备

- 路由与导航：`inbound-approvals`、`outbound-approvals` 已在应用路由目录声明。
- 权限代码：`stock.inbound.approve`、`stock.outbound.approve` 已存在。
- 查询能力：入库、出库列表都支持 `status=pending`、关键词、创建时间范围和服务端分页。
- 详情能力：`GET /api/inbound/{id}`、`GET /api/outbound/{id}`。
- 审批能力：入库和出库均有 approve、reject 接口，且成功响应返回更新后的完整单据。
- 展示基础：现有入库单、出库单页面已经有物品名称、SKU、单位、图片、状态和详情呈现模式。

### 已实施的权限组合

审批页不仅调用 approve/reject，还必须读取列表和详情。当前后端读取接口分别要求 `stock.inbound.read`、`stock.outbound.read`，但审批路由元数据只检查 approve 权限。

当前规则：

- 入库审批页要求同时拥有 `stock.inbound.read` 与 `stock.inbound.approve`。
- 出库审批页要求同时拥有 `stock.outbound.read` 与 `stock.outbound.approve`。
- 路由元数据和守卫应支持 `requiredPermissions` 全部满足；导航也使用同一判断，避免用户进入后才连续收到 `403`。
- 如果产品决定“approve 权限天然包含读取”，则应由 core 明确放宽列表和详情授权并同步权限文档，不能只在前端假定权限包含关系。

路由元数据、守卫和导航已经使用该组合；普通单权限页面继续兼容原有 `requiredPermission`。

## HTTP 契约

| 领域 | 队列                               | 详情                     | 通过                                              | 拒绝                                             |
| ---- | ---------------------------------- | ------------------------ | ------------------------------------------------- | ------------------------------------------------ |
| 入库 | `GET /api/inbound?status=pending`  | `GET /api/inbound/{id}`  | `POST /api/stock-approvals/inbound/{id}/approve`  | `POST /api/stock-approvals/inbound/{id}/reject`  |
| 出库 | `GET /api/outbound?status=pending` | `GET /api/outbound/{id}` | `POST /api/stock-approvals/outbound/{id}/approve` | `POST /api/stock-approvals/outbound/{id}/reject` |

列表继续使用 `page`、`page_size`、`search`、`date_from`、`date_to`。审批页固定发送 `status=pending`，不提供已通过、已拒绝状态筛选；历史结果应回到入库单或出库单页面查询。

审批动作当前没有请求体，因此首版：

- 不展示“审批备注”。
- 不要求填写“拒绝原因”。
- 不伪造本地备注或把原因拼进其它字段。
- 若后续确需审批意见，先扩展 core DTO、审计事件和 OpenAPI，再增加输入控件。

## 两页共享与差异

| 范围       | 入库审批                       | 出库审批                           | 是否共享实现           |
| ---------- | ------------------------------ | ---------------------------------- | ---------------------- |
| 队列状态   | 只查 `pending`                 | 只查 `pending`                     | 是                     |
| 搜索       | 单号、来源、物品、批次         | 单号、去向、物品、批次             | 是，提示词配置化       |
| 通过结果   | 创建批次并增加库存             | 指定批次或 FIFO 扣减库存           | 动作相同，后果文案不同 |
| 拒绝结果   | 不增加库存                     | 不扣减库存                         | 是，文案配置化         |
| 核心上下文 | 来源、库位、单价、批次、有效期 | 去向、限制库位、指定批次或 FIFO    | 详情明细插槽不同       |
| 主要风险   | 库位被删除                     | 库存不足、指定批次不可用、并发扣减 | 错误映射不同           |
| 权限       | inbound read + approve         | outbound read + approve            | 是，权限配置化         |

## 页面目标

- 让审批人只处理当前仍为 pending 的单据，不把历史查询和审批任务混在一起。
- 在执行不可逆库存变更前，完整展示单据身份、物品、数量、库位/批次规则和业务后果。
- 单次审批只作用于一张单据；首版不做批量通过或批量拒绝。
- 服务端始终是最终状态与库存判断来源；前端不根据旧列表数据预测审批一定成功。
- 审批成功后自然进入下一张待审批单据，适合连续工作，同时保留返回队列的明确路径。

## 页面信息架构

```text
页面标题“入库审批”或“出库审批”
├─ 工具栏
│  ├─ 关键词搜索
│  ├─ 待审批总数
│  ├─ 创建时间筛选
│  └─ 刷新
├─ 待审批队列
│  ├─ 桌面三段式列表 / 移动单列条目
│  └─ 尾部触底加载、失败重试、已加载全部
└─ 审核详情 Dialog
   ├─ 库存影响：状态、通过后变化、提交时间和事务后果
   ├─ 单据信息：来源/去向、创建时间、创建人和备注
   ├─ 业务明细
   └─ 关闭 / 拒绝 / 通过
```

页面不使用常驻左右双栏。审核详情是临时任务，使用宽 `ModalDialog`；移动端按现有规则占满可用视口。这样可以复用项目既有详情模式，也不会在未选中单据时长期保留空白详情列。

## 标题与工具栏

### 页面标题

- 桌面显示路由标题；副标题分别为“审核待入库单据，确认后写入批次与库存”和“审核待出库单据，确认后扣减库存”。
- 移动 Shell 已显示路由标题时，页面内部不重复同名大标题。
- 标题区不放创建入口；新建入库、新建出库仍属于各自工作台。

### 搜索

- 复用 `SearchField`。
- 入库提示词：“搜索单号、来源、物品或批次”。
- 出库提示词：“搜索单号、去向、物品或批次”。
- 防抖后写入 URL `search` 并重新加载第 1 页；取消旧请求不显示错误。
- 搜索仅由服务端执行，不过滤已加载页。

### 筛选

- 首版只提供创建时间范围，复用 `DateTimeField` 和小型筛选 Dialog。
- 不提供状态筛选，因为页面固定为 pending 队列。
- 筛选按钮角标只统计开始时间、结束时间两个有效条件。
- “重置”只修改 Dialog 草稿；“应用筛选”才更新 URL 和请求。
- 开始时间晚于结束时间时显示字段错误，不发送请求。

### 数量与刷新

- 工具栏显示“待审批 N 条”，该数字来自服务端 `total`。
- 刷新保留旧列表、滚动位置和筛选条件；按钮显示稳定等待状态。
- 刷新期间不清空列表，不用整页骨架替换可用内容。

## 待审批队列

### 桌面三段式结构

```text
固定身份区 | 弹性业务摘要区 | 固定判断与操作区
```

身份区：

- `入库单 #<id>` / `出库单 #<id>`。
- 来源或去向；缺失时使用稳定回退文案。
- 创建时间。
- 创建人只能在已有 ID 时显示“用户 #<id>”，不逐行请求用户姓名。

业务摘要区：

- 第一件物品的鉴权图片、名称、SKU。
- `n 条明细` 与数量摘要。
- 入库可显示金额合计；混合单位不伪造总数量。
- 出库显示“指定批次”或“审批时 FIFO”，但不得声称库存一定充足。

判断与操作区：

- 固定标签“待审批”。
- 展示等待时长，例如“等待 2 小时”；同时保留可访问的完整创建时间。
- 使用带信息图标的“查看详情”次级按钮，点击打开审核详情；按钮提供对应领域的 `title` 与包含单号的 `aria-label`。
- 整行可点击并支持 Enter、Space；行点击只打开详情，不直接执行写操作。

### 移动单列条目

- 第一行：单号、待审批标签；卡片内提供带信息图标的“查看详情”次级按钮，窄屏时独占一行以保持触控尺寸和可发现性。
- 第二行：来源/去向与创建时间。
- 第三块：第一件物品、明细数、数量或扣减方式摘要。
- 不使用横向滚动，不把通过、拒绝直接放在列表卡片上。
- 触控目标不小于项目移动控件标准，长文本两行截断，全文在审核详情中展示。

### 排序边界

当前列表接口没有公开排序参数，首版沿用服务端现有稳定顺序，不在前端对分页结果重新排序。若业务要求严格“先提交先审批”，应增加服务端排序契约并让列表查询与 `total` 共同使用，不能只排序已加载页。

## 审核详情 Dialog

### 打开与加载

- 点击队列项后立即打开 Dialog，先使用列表数据展示单号、来源/去向和创建时间。
- 同时按需请求详情接口；详情未成功加载前，通过和拒绝按钮保持禁用。
- 切换单据时取消上一个详情请求，只允许最新响应写入当前会话。
- 详情返回状态已不是 pending 时，不显示动作按钮，提示“该单据已由其他操作处理”，关闭后刷新队列。

### 库存影响与单据信息

- Dialog 正文只保留“库存影响、单据信息、业务明细”三个层级；状态和提交时间合并进入库存影响区，不再建立独立上下文条，也不重复显示来源/去向。
- 正文由统一网格管理区块间距，桌面使用 `18px`、移动使用 `14px`，各区块不再叠加独立外边距。
- 单据编号、状态、来源/去向、创建时间、创建人、备注。
- 明细条数；数量按明细展示，只有单位完全相同时才允许汇总。
- 顶部只出现一次库存语义，不在每个区块重复说明。
- 不使用禁用表单模拟详情，使用只读键值组和连续明细列表。

### 入库审批详情

每条明细显示：

- 物品图片、名称、SKU、物品 ID、单位。
- 数量、单价、行金额。
- 目标库位。
- 批次号、有效期。

库存影响区固定表达：

- 通过：“将为全部明细创建批次并增加对应库位库存，同时写入库存流水和审计事件。”
- 拒绝：“只把单据标记为已拒绝，不创建批次、不增加库存。”

审批前不允许前端编辑库位、批次号或有效期。若信息错误，应拒绝并由创建方重新提交；当前 API 不支持审批页修单。

### 出库审批详情

每条明细显示：

- 物品图片、名称、SKU、物品 ID、单位。
- 申请数量。
- 可选限制库位。
- 指定批次 ID，或“未指定批次，审批时按 FIFO 分配”。
- FIFO 规则简洁显示为“有效期优先，其次按入库时间和批次顺序”，详细数据库排序不作为常驻说明。

库存影响区固定表达：

- 通过：“服务端将在同一事务内重新检查库存，并按指定批次或 FIFO 扣减；任一明细失败则整张单据不生效。”
- 拒绝：“只把单据标记为已拒绝，不扣减库存。”

当前响应没有可靠的实时可用量预检字段，因此不展示绿色“库存充足”结论。即使未来展示快照，也必须明确最终以审批事务的实时检查为准。

## 通过与拒绝交互

### 动作位置与等级

- Dialog 底部顺序：`关闭`、`拒绝`、`通过`。
- “通过”使用主按钮；“拒绝”使用危险次级按钮，不使用与删除相同的强危险填充，避免夸大语义。
- 动作期间三个按钮全部禁用，关闭入口也暂时禁用，防止请求结果丢失。

### 确认阶段

点击通过或拒绝后，不叠加第二个 ModalDialog；在当前审核 Dialog 内进入确认状态：

- 保留单号和动作后果。
- 通过确认文案明确“增加库存”或“扣减库存”。
- 拒绝确认文案明确“拒绝后不能再次审批”。
- 提供“返回检查”和“确认通过/确认拒绝”。
- 不使用仅靠颜色区分的确认状态。

### 成功结果

- 使用服务端返回的单据确认最终状态，不做请求前乐观移除。
- 成功 Notice：入库“入库单 #ID 已通过，库存已增加”；出库“出库单 #ID 已通过，库存已扣减”；拒绝使用“单据 #ID 已拒绝，库存未变更”。
- 当前项从 pending 队列移除，总数按服务端成功结果减一，并后台重新协调队列，避免分页因删除产生跳项。
- 若还有下一项，Dialog 切换到下一张并重新加载详情；提供短暂且可撤销的“返回队列”路径，不自动执行任何下一步动作。
- 若队列为空，关闭 Dialog 并显示完成空状态。

## 错误与并发处理

| 场景                     | 页面行为                                                                 |
| ------------------------ | ------------------------------------------------------------------------ |
| `400` 单据数据无效       | 保留详情，指出需要创建方修正；不允许审批页直接改字段。                   |
| `403`                    | 关闭写操作，提示权限已变化；重新同步会话权限并离开不可访问路由。         |
| `404`                    | 提示单据不存在或已不可读取，关闭详情并刷新队列。                         |
| `409 order_not_pending`  | 提示已被其他人处理，移出当前队列并加载下一项。                           |
| `409 insufficient_stock` | 保留出库详情，提示库存不足或批次不可用；允许返回检查或拒绝，不伪造成功。 |
| 入库库位不可用           | 保留详情并显示服务端稳定错误；建议拒绝后重新提交。                       |
| 网络失败                 | 保留 Dialog、详情和用户上下文，恢复按钮并允许重试；不移除队列项。        |

每张单据同一时间只允许一个动作请求。双击、键盘重复提交或两个按钮快速切换都必须被本地互斥锁阻止；服务端 `409` 继续作为多用户并发的最终保护。

## 列表与异步状态

- 初次无数据：加载提示延迟 200ms，出现后至少保持 350ms。
- 后台刷新：旧队列保持可见，降低局部透明度并让刷新按钮等待。
- 触底追加：使用尾部哨兵；加载失败只在尾部显示重试，不替换已有队列。
- 无待审批单据：显示“当前没有待审批入库单”或“当前没有待审批出库单”，不显示新建入口。
- 搜索或日期无结果：显示“没有符合条件的待审批单据”和“清除筛选”。
- 有旧数据时刷新失败：保留旧数据，通过 Notice 报告。
- URL 保存 `search`、`date_from`、`date_to`；不保存打开的 Dialog 或确认阶段，刷新后回到稳定队列。

## 响应式与可访问性

### 桌面 `1440 × 900`

- 工具栏、列表、尾部位于一个连续工作区。
- 三段式列表左右固定区在横向滚动时保持位置不变；宽度足够时不得出现横向滚动。
- 审核 Dialog 使用宽规格，但不得超过视口可用高度；标题、内容、操作区分别稳定，只有内容区滚动。

### 断点附近约 `768px`

- 工具栏允许搜索独占一行，数量与图标操作保持同组。
- 列表切换为紧凑单列条目，不维持不可读的三列压缩。
- Dialog 操作区保持“关闭 / 拒绝 / 通过”顺序，不因换行改变危险操作位置。

### 移动 `390 × 844`

- 页面不重复 Shell 标题。
- 审核 Dialog 占满可用视口，底部操作区考虑安全区并保持可见。
- 内容区独立滚动；打开、关闭和确认切换不造成背景滚动穿透。
- 硬件返回或浏览器返回优先退出确认阶段，其次关闭审核详情，最后才离开路由。

### 可访问性

- 队列使用正确的 list/table 语义，行可通过键盘打开。
- Dialog 打开后焦点进入标题或首个可操作元素，关闭后返回原队列项；原项已被审批移除时返回下一项或队列标题。
- 状态、库存影响和错误必须有文字，不仅依赖颜色。
- 动作等待使用 `aria-busy`；Notice 与局部错误按紧急程度使用 `status` 或 `alert`。
- 遵守 `prefers-reduced-motion`，审批成功后的移除与下一项切换不使用大幅滑动。

## 建议模块划分

```text
frontend/src/api/stockApprovals.ts
```

## 验收矩阵

- 权限：缺 read、缺 approve、同时具备、会话中权限被撤销。
- 队列：无数据、单条、多页、搜索无结果、日期无结果、触底失败、后台刷新失败。
- 详情：多明细、混合单位、缺图片、缺备注、长来源/去向、详情 404/403/网络失败。
- 入库通过：正常增加库存、库位被删除、重复审批。
- 出库通过：指定批次成功、FIFO 成功、库存不足、批次不可用、并发扣减、重复审批。
- 拒绝：正常拒绝、重复拒绝、其他审批人抢先处理；确认没有库存变化。
- 连续审批：成功后进入下一项、最后一项完成、焦点恢复、列表 total 与实际队列一致。
- 视口：`1440 × 900`、约 `768px`、`390 × 844` 的真实尺寸、横向溢出、Dialog 滚动和安全区。
- 浏览器：控制台无新增 error、warning、issue；无背景滚动穿透；键盘和减少动态效果可用。
- 工程：`pnpm build`、相关前端检查、`git diff --check` 通过；源码中文文件注释、公共类型注释和过时注释已核对。

## 明确非目标

- 不做批量审批、批量拒绝、审批人分配、审批优先级或 SLA 看板。
- 不在审批页编辑单据、库位、批次或数量。
- 不新增审批备注或拒绝原因，除非后端契约先支持。
- 不在前端预扣、预增库存，也不把列表快照当作审批成功保证。
- 不把 approved、rejected 历史记录混入审批队列；历史查询继续归入库单、出库单页面。
- 不新增第三方表格、状态管理、日期或工作流依赖。
