# 列表滚动与响应式切换整改分析

## 结论

当前前端的列表滚动问题主要来自两个规则没有统一：

1. 主列表仍以固定最小列宽的桌面表格为基线，视口或应用内容区变窄后才出现横向滚动。
2. 切换到卡片后，部分结果区仍保留 `overflow: auto`，形成“应用壳滚动 + 列表区域滚动”的双重纵向滚动。

整改目标不是删除所有滚动，而是让滚动拥有明确边界：

- 主页面列表在卡片模式下由应用内容区负责纵向滚动。
- 桌面宽表格只在实际列表容器足够宽时启用；不足时直接切换卡片，不允许依赖横向滚动访问业务字段或操作。
- Dialog、分组树、批次选择和草稿编辑器等有明确高度约束的复杂子列表可以保留内部滚动，但需要保持单一滚动区域。
- 断点按列表容器宽度决定，不按浏览器视口宽度决定，避免侧栏、权限或布局变化造成临界宽度错判。

## 当前滚动边界

应用壳已经提供主内容滚动容器：[`AppShell.scss`](../../src/layouts/AppShell.scss) 的 `.app-content-pane`（约 86-94 行）设置了 `overflow-y: auto`。但是多个页面又给结果区设置 `overflow: auto`，导致同一业务页面存在第二个纵向滚动容器。

这在桌面宽度下有时是为了保持工具栏和表头稳定，不能简单全局删除。应把规则分成两种模式：

```text
宽桌面且使用表格：工作区内的结果区可以滚动，表头可 sticky
容器宽度不足或使用卡片：结果区 overflow: visible，由应用内容区滚动
```

卡片模式还必须关闭表格的 `min-width` 约束；仅设置 `overflow-x: hidden` 不算修复，因为它会把可访问内容直接裁掉。

## 根因分析

### 1. 断点按视口而不是列表容器计算

桌面应用在 `768px` 以后仍可能包含 `224px` 左侧导航、页面内边距和工作区边界。用 `@include mixins.tablet(900px)` 或 `@include mixins.mobile` 判断表格是否能容纳列宽，会把浏览器视口宽度误当成列表实际宽度。

例如，单据表格要求约 `760px`，但视口为 `900px` 时，扣除侧栏和内容边距后列表实际宽度可能已经不足；视口只增加几个像素也不会真正解决问题。

### 2. 用滚动容器掩盖布局切换缺失

`overflow: auto` 同时处理横向和纵向溢出，短期内不会撑破工作区，但用户必须横向寻找字段和操作按钮。`SubstitutesPage.scss` 在窄宽度设置 `overflow-x: hidden` 更危险：内容不可见，且不会触发任何可访问性反馈。

### 3. 卡片模式和列表模式的滚动所有权没有同时切换

部分页面已经具备移动卡片 DOM，但只切换了 `display` 和列布局，没有同步切换结果区的滚动策略。卡片模式下结果区继续 `overflow: auto`，页面外层也可滚动，容易出现滚轮/触摸手势停在内层、尾部哨兵不自然触发和移动端内容高度计算异常。

### 4. 入库/出库存在展示模板重复

入库页复用 `InboundOrderList`，出库页在页面模板中再次维护 `.inbound-orders-table` 和 `.inbound-orders-mobile-list`，并通过导入同一套样式获得外观。这使滚动边界和断点修复必须同时检查两套模板，后续容易再次分叉。

## 统一整改方案

### A. 建立容器宽度驱动的列表切换

在页面结果工作区或列表外壳上设置 `container-type: inline-size`，表格与卡片视图继续复用同一份查询数据和尾部哨兵：

```text
容器宽度 >= 表格最小列宽 + 内边距：桌面表格
容器宽度 < 表格最小列宽 + 内边距：移动/窄桌面卡片
```

建议初始测量阈值：

| 列表        | 表格基准最小宽度 |        初始切换参考 |
| ----------- | ---------------: | ------------------: |
| 物品目录    |            720px |          744px 左右 |
| 入库/出库单 |            760px |          784px 左右 |
| 审批队列    |            760px |          784px 左右 |
| 库位        |            740px |          764px 左右 |
| 替代关系    |            700px |          724px 左右 |
| 慢动物品    |            620px |          644px 左右 |
| 用户管理    |            864px | 现有 864px 容器边界 |

这些值是布局初始值，不是最终产品断点；必须在真实卡片最小可读宽度、按钮宽度和内边距确定后校准。

### B. 明确两种滚动模式

宽表格模式：

- 结果区可以 `overflow-y: auto`，但必须确认工作区高度约束存在。
- 横向方向使用 `overflow-x: hidden` 只是表格已满足容器宽度后的保护措施，不能用来遮挡未处理的表格。
- 表头 sticky 只属于表格模式。

卡片模式：

- 结果区使用 `overflow: visible`，`flex` 不再锁死内容高度。
- 卡片列表和触底哨兵自然撑开结果区，由 `.app-content-pane` 负责页面滚动。
- 卡片不得保留桌面表格的 `min-width`、固定列、sticky 右侧操作区或横向滚动。

### C. 优先复用现有结构

- 复用 `UserDirectoryMobileList` 的容器查询切换方式作为边界参考。
- 复用 `InboundOrderList` 作为入库/出库单的共享列表壳，出库字段通过配置或受控插槽提供，不再复制整段模板。
- 复用 `ApprovalQueueList` 的桌面/移动双视图，但把其断点从视口媒体查询迁移到列表容器。
- 不新引入表格库或通用“大而全”响应式列表组件；不同业务的字段和操作密度不同，共享应集中在滚动边界、断点约定和少量样式原语。

## 实施顺序

1. 先整改入库/出库单与审批队列，验证共享列表、触底哨兵和详情 Dialog 在同一滚动策略下工作。
2. 整改物品目录和库位管理，处理字段密度最高的表格以及库位分组树的双面板边界。
3. 整改替代关系和总览慢动物品表，清理 `overflow-x: hidden` 和窄桌面横向表格。
4. 对用户管理只做边界校准；模板页只检查顶部选项卡，不把它当作主列表问题。
5. 最后单独复核草稿、批次选择和 Dialog 内部滚动，避免把有意的固定高度操作区误改成页面长列表。

## 验收矩阵

每个主列表至少检查 `1440 × 900`、`1200 × 800`、`1024 × 768`、`900 × 768`、`768 × 900` 和 `390 × 844`。断点检查应以列表实际容器宽度为准，而不是只记录浏览器视口。

- 表格模式的列头、固定操作区、长文本省略和 sticky 行为正常。
- 卡片模式不出现页面级或结果区横向滚动；`scrollWidth` 不超过对应容器宽度。
- 卡片模式只有应用内容区承担纵向滚动，触底哨兵可到达并能继续加载。
- 从表格切到卡片前不出现一像素横向滚动，切换后不会保留桌面固定列宽。
- 刷新、筛选、空状态、初始错误、追加失败和已加载全部状态不会改变滚动所有权。
- 详情 Dialog、分组树、批次选择等有意内部滚动的区域，标题/操作区仍固定且只存在一个内容滚动节点。
- 键盘焦点、Enter/Space 行操作、触控目标、`aria-busy` 和控制台错误保持现有契约。
