# 用户管理页面重设计方案

## 1. 目标与边界

当前 `frontend/src/pages/UsersPage.vue` 属于早期页面实现。它使用三段嵌套 CSS Grid 组织用户列、中间账号信息列和操作列，列宽由多层 `1fr` 共同分配，导致窗口变宽时“最近更新”列吞掉大量无意义空间；操作按钮较多时还会反向撑出横向滚动。

本方案的目标是重新设计用户管理页面的信息架构和页面级布局，使它符合 WineStock 当前的中性业务工具风格：

- 桌面端适合管理员连续扫描、比较和执行账号操作。
- 列宽具有明确的内容边界，不把剩余空间塞进某一列。
- 移动端保留同一份数据和权限逻辑，使用更适合触控的纵向管理列表。
- 继续使用现有 HTTP API、权限判断、Notice、异步状态和用户 Dialog。
- 不引入新的后端接口，不复制一套用户业务逻辑。

本方案只改变前端页面结构和视觉交互，不改变账号安全策略、服务端授权、用户分页协议和登录会话行为。

## 2. 现有能力保留

以下行为必须原样保留：

- 路由仍为 `/users`，进入权限仍为 `user.read`。
- 用户名搜索、账号状态筛选、刷新和服务端分页继续使用现有实现。
- 创建用户、修改用户名、修改权限、设置临时密码、启用/停用和软删除继续调用现有 API。
- 前端只根据权限快照收敛入口，后端仍是最终授权边界。
- 当前用户不能从页面停用、删除或重置自己的临时密码。
- 编辑当前账号权限时继续锁定安全相关权限，并在保存成功后同步会话权限快照。
- 列表初次加载、后台刷新、失败重试和取消旧请求继续遵守 `200ms` 延迟、`350ms` 最短展示和保留旧结果规则。
- 操作成功和失败继续使用全局 Notice，不在页面内增加常驻说明卡片。
- 现有 `UserCreateDialog`、`UserUsernameDialog`、`UserPermissionsDialog`、`UserPasswordResetDialog`、`UserStatusDialog`、`UserDeleteDialog` 继续复用。

## 3. 新页面信息架构

页面保持已登录 `AppShell` 的顶部栏、左侧导航和内容区结构，不增加第二层导航或独立后台壳。

```text
用户管理
  页面标题行
    用户管理
    用户总数 / 当前筛选结果
    创建用户
  用户列表工作区
    列表工具栏
      搜索用户名
      账号状态
      刷新
      当前结果数量
    用户列表
      列表表头（桌面）
      用户行（桌面）
      用户管理项（移动端）
      触底加载哨兵 / 已加载全部提示
```

页面标题行只负责页面身份和主操作。搜索、状态和刷新属于列表工具栏，不能再混入页面标题区。

## 4. 桌面端布局

### 4.1 列表结构

桌面端使用单层、直接列模型。可以使用语义 `<table>`，或者使用同一层级的 Grid 行，但不得再把中间列包进第二层 Grid 后由多个 `1fr` 级联分配。

推荐列模型：

| 列       | 建议宽度             | 说明                                                                                                |
| -------- | -------------------- | --------------------------------------------------------------------------------------------------- |
| 用户     | `180px`              | 保留用户名、`#ID` 和当前账号标记，不让短用户名吞掉操作区；超长用户名省略，完整值通过 `title` 保留。 |
| 状态     | `88px`               | 状态标签稳定对齐。                                                                                  |
| 权限     | `92px`               | 展示权限数量，不让数量列扩张。                                                                      |
| 密码     | `104px`              | 展示“正常 / 待修改”状态。                                                                           |
| 最近更新 | `148px`              | 日期内容列，宽度由格式和内边距覆盖，不使用 `1fr`。                                                  |
| 操作     | `minmax(240px, 1fr)` | 直接容纳当前权限下的全部桌面操作。                                                                  |

核心原则是：用户名列保持较窄且有限的宽度，剩余空间优先给桌面操作列；日期、状态、权限和密码列采用稳定宽度。这样不会让短用户名占据大半工作区，也不需要用二级菜单隐藏常用操作。

### 4.2 行内容

用户列使用两级身份层级：

- 第一行显示用户名，使用较高字重。
- 第二行显示 `#ID`，当前账号附加轻量“当前账号”标记。

状态、权限和密码列只显示一个明确值，不重复解释状态含义。最近更新使用 `<time>`，保留机器可读的 `datetime` 和完整值提示。

桌面操作列直接展示当前账号可执行的操作：

- 修改用户名、权限、临时密码、启用/停用和删除按权限直接显示。
- 操作列使用足够的固定最小宽度，不让用户名列无意义地吞掉工作区空间。
- 危险删除在操作列末尾使用危险色，不引入桌面二级菜单。

移动端由于宽度受限，继续使用现有 `UserActionsDialog` 作为唯一管理入口；桌面和移动端不复制权限判断。

### 4.3 工作区宽度和滚动

- 列表工作区使用父容器宽度，但表格自身不再人为制造日期列的弹性空白。
- 当用户列表内容区小于桌面表格的 `864px` 最小完整宽度时，沿用操作日志页面的响应式模式，隐藏桌面表格并显示纵向用户卡片；切换发生在滚动条出现之前。
- 用户列表内容区不小于 `864px` 时，桌面表格直接容纳当前权限下的全部操作；用户列和操作列有明确边界，不使用多层弹性列分配。
- 桌面操作列直接容纳常用命令；只有移动端使用单个管理入口。
- 表头、数据行和空状态必须共享同一列模型，不能分别计算宽度。

## 5. 移动端布局

窄桌面和移动端在列表内容区小于 `864px` 时切换为纵向用户管理列表，不渲染桌面表头和横向表格；`768px` 以下继续由 AppShell 重排为移动壳层。

每个用户项的结构：

```text
用户身份                           管理操作图标
用户名
#ID · 当前账号
---------------------------------------
状态       权限
已启用     26 项
密码       最近更新
正常       2026/08/03 14:41
```

规则：

- 用户名和管理入口处于第一行，长用户名省略但不推动操作按钮。
- 详情区域只保留一条分隔线，不使用卡片套卡片或过度圆角。
- 操作入口只有一个管理图标按钮，打开现有 `UserActionsDialog` 或页面级操作 Sheet。
- 删除在操作列表中使用独立分隔和危险色。
- 工具栏第一行放搜索、刷新和创建，第二行放状态筛选和结果数量，延续现有用户管理文档约定。
- 触控目标至少 `44px`，操作面板和 Dialog 继续由共享组件处理焦点、Escape 和关闭行为。
- `390px` 视口不得出现横向溢出，用户项内容不得遮挡管理按钮。

## 6. 组件职责调整

暂不拆分新的业务状态层，先沿用现有 `UsersPage.vue` 的数据和操作编排。

建议的前端职责：

- `UsersPage.vue`：保留请求、筛选、分页、权限判断、操作 Dialog 编排和列表刷新。
- `UserListToolbar.vue`：保留搜索、状态、结果数量、刷新和创建入口；只调整视觉排列。
- 新增 `UserDirectoryTable.vue`：拥有桌面端表头、用户行、列模型和桌面操作入口，向页面发出统一操作事件。
- 新增 `UserDirectoryMobileList.vue`：拥有移动端用户项和管理入口；只接收用户数据和事件，不拥有 API。
- `UserActionsDialog.vue`：继续作为移动端操作选择器；如果桌面也采用更多菜单，可提炼其中的操作定义，但不复制权限判断。
- 现有用户 Dialog：保持单一操作职责和现有安全文案，不把表单搬回列表行。
- `UsersPage.scss`：只拥有页面级工作区、桌面列模型、移动列表和列表状态；共享按钮、表单、Dialog 和 Notice 样式继续由所属组件维护。

如果桌面更多菜单和移动操作 Sheet 最终使用完全相同的动作集合，可以新增纯数据型 `userActions.ts`，只负责动作标签、图标语义和危险标记；权限判断仍留在页面或权限 composable，不把权限规则下沉到展示数据中。

## 7. 状态和交互细节

### 初始加载

- 初次请求超过延迟阈值后显示稳定尺寸的列表骨架。
- 页面标题和工具栏保持可见，不能因列表请求清空整个工作区。
- 失败显示页面级错误状态和重试入口，但保留工具栏。

### 搜索、筛选和刷新

- 搜索和状态筛选继续重建第一页请求。
- 旧列表在后台请求期间保持可见，只做轻微弱化和刷新按钮状态变化。
- 过滤后没有结果时隐藏表头和空表格，显示单一空状态，并提供清除当前筛选入口。
- 结果数量只在工具栏显示一次，不在标题、表头和列表底部重复。

### 行操作

- 打开操作菜单前记录触发按钮，关闭后恢复焦点。
- 操作提交期间锁定当前 Dialog 操作区，保留目标用户上下文。
- 成功后只更新或重建必要列表数据，不让整个页面闪烁。
- 修改当前账号用户名或权限后立即同步页面顶部当前用户和导航权限快照。

### 分页

- 继续使用服务端分页作为数据获取协议。
- 界面仍采用列表尾部哨兵触底加载，不增加上一页/下一页翻页器。
- 加载下一页时保留已有列表，底部只显示局部加载反馈。
- 已加载全部后显示一次底部状态。

## 8. 视觉约束

- 使用当前中性业务工具风格、系统字体、现有主题 token 和低饱和状态色。
- 页面主体不增加指标卡片、渐变、装饰图形或营销式大留白。
- 页面工作区可以是一个完整的列表区域，但不能在列表外再套重复卡片。
- 普通行高度建议桌面 `60px` 左右，移动项按内容自然增长但保持紧凑。
- 普通桌面操作使用简短文字命令，移动端使用单个管理图标入口；创建、保存、确认等明确命令继续使用文字按钮。
- 日期、状态、权限数量和操作列必须有稳定宽度或明确最大宽度。
- 不用负 margin、隐式溢出或 sticky 偏移修正列宽问题。
- 所有动画复用 motion token；后台刷新遵守异步状态文档，不用新计时器。

## 9. 实施顺序

1. 先恢复当前 `UsersPage.scss` 的手动回退状态，确认工作区只保留用户已有改动。
2. 根据本方案补充桌面列模型和移动项的页面级结构草图，不接入新 API。
3. 新增桌面列表展示组件，先接入现有用户数据和事件，替换旧表格 DOM。
4. 新增移动列表展示组件，复用现有移动操作 Dialog 和数据状态。
5. 调整 `UserListToolbar` 的布局，使桌面、窄桌面和移动端控件位置稳定。
6. 接入现有 Dialog、Notice、稳定刷新状态和触底加载哨兵。
7. 删除旧页面结构中不再使用的 Grid、固定列和旧操作按钮样式；不删除用户管理 Dialog 或 API 文件。
8. 更新 `frontend/docs/user-management.md`、`frontend/docs/code-map` 对应页面职责和验收记录。

## 10. 验收标准

### 功能

- 所有现有用户管理 API 和权限行为保持通过。
- 创建、编辑用户名、权限、临时密码、启停和删除操作均能从新布局进入。
- 当前账号保护、最后权限管理员保护和错误 Notice 不回归。
- 搜索、筛选、刷新、触底加载、空结果和失败重试行为不回归。

### 视觉和布局

- `1280x800`：最近更新列只覆盖日期内容和内边距，末尾不出现成片空白。
- 列表内容区小于 `864px`：切换为纵向用户卡片，不出现页面级或列表横向溢出。
- 列表内容区达到 `864px`：桌面表格与纵向卡片切换不重叠、不闪烁。
- `390x844`：移动用户项、管理入口和状态信息不遮挡，页面无横向溢出。
- 操作按钮数量变化不会改变表头列位置，也不会将最后一个操作裁切在容器外。
- 明暗主题继续使用同一结构和语义 token。

### 工程验证

- `pnpm exec prettier --check` 覆盖新增和修改的 Vue/SCSS 文件。
- `pnpm build` 通过。
- 使用 Chrome DevTools MCP 在目标视口读取真实 `getBoundingClientRect()`、`scrollWidth`、`clientWidth` 和计算样式。
- 检查列表、菜单、Dialog 的键盘焦点、Escape、关闭后焦点返回和浏览器控制台。
- 变更后确认 `git diff` 只包含新页面实现和对应文档、代码地图，不回退用户已有改动。

## 11. 暂不做的事情

- 不新增用户详情后端接口。
- 不把用户管理改成独立路由或独立 Shell 页面。
- 不引入新的表格组件库。
- 不把权限规则、账号安全判断或 API 请求复制到展示组件。
- 不删除当前 `UsersPage.vue`、用户管理 Dialog 或现有页面文档；新布局验证通过后再由实现提交逐步替换旧 DOM。
