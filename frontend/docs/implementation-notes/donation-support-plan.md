# WineStock 捐赠支持方案

## 1. 目标与范围

WineStock 已具备稳定的库存管理工作流。本方案增加一个低打扰的「支持 WineStock」入口，并在用户形成一定使用习惯后主动提示捐赠。

本次方案只覆盖共享前端，不新增 core HTTP API、数据库表、账户字段或平台原生支付能力：

- 捐赠方式由前端展示二维码。
- 展示入口、提示控制器和本机计数均由 `frontend` 拥有。
- Desktop 和 Android 复用同一套 Vue 组件；不新增平台原生支付能力。
- 不记录支付结果、金额、交易号、银行卡或其它支付信息。
- 不将捐赠计数上传服务器，也不把捐赠行为作为业务权限或登录条件。

## 2. 用户入口

### 2.1 账户弹层中的永久入口

现有 `AppShell` 顶部头像已统一承载账户和本机选项，`AccountPopover` 已包含偏好设置、本机运行设置、联系与反馈、局域网地址和退出登录。因此捐赠入口直接加入该弹层：

```text
头像
  ├─ 偏好设置
  ├─ 本机运行设置
  ├─ 支持软件
  ├─ 联系与反馈
  ├─ 本机局域网地址（满足条件时显示）
  └─ 退出登录
```

建议使用「支持软件」作为菜单文案，而不是「捐赠」，因为前者更自然，也能覆盖请作者喝咖啡、赞助开发等不同方式。

入口规则：

- 只要 `donationEnabled` 为 true，入口始终可用，不受自动提示的关闭状态影响；为 false 时整个入口隐藏。
- 点击入口后关闭账户弹层，再打开统一的捐赠 Dialog。
- 打开 Dialog 后焦点回到账户触发按钮；关闭、Escape 和原生返回均遵循现有 `ModalDialog` 规则。
- 不在主导航、库存列表工具栏或新增物品按钮旁添加常驻捐赠按钮，避免干扰主要工作流。

### 2.2 自动提示

当 `donationEnabled` 为 true 时，自动提示使用与永久入口相同的 Dialog，不复制二维码或支付链接；为 false 时控制器完全停用。

推荐使用累计里程碑，而不是每次达到一个阈值后重新按相对计数触发：

| 条件         |            累计里程碑 | 计数方式                                  |
| ------------ | --------------------: | ----------------------------------------- |
| 应用打开     |          10 次、50 次 | 进入已登录应用壳或本机静默应用壳后计 1 次 |
| 成功新增物品 | 50 件、100 件、300 件 | 以服务端确认创建成功的物品数量计数        |

共 5 个里程碑，每个里程碑最多触发一次自动提示。两个条件采用「或」关系：任一未处理里程碑达到时，都可以进入待提示状态。控制器配置应集中保存里程碑，后续可以调整阈值而不改变 UI。

如果用户在一次提示后又跨过了多个里程碑，不连续弹出多个 Dialog。控制器保存未处理里程碑，按照达到时间顺序排队；只有下一次有效进入应用时才检查队列并最多提示一个，新增物品成功本身不直接触发提示。

提示不应在页面刚加载或用户正在填写表单时突然出现。控制器只发出「请求提示」事件，应用壳负责在以下条件满足后打开 Dialog：

- 当前没有其它 Dialog、Drawer、全屏加载层或错误覆盖层。
- 当前没有进行中的新增、保存、导入、提交或路由切换。
- 触发事件完成后至少等待约 `1000ms`，让成功 Notice 先完成展示。
- 用户仍处于 WineStock 应用壳内。

如果当前不适合展示，提示请求保留到本次会话的空闲时机，但不应在用户离开应用后强行弹出。

## 3. 捐赠 Dialog 设计

### 3.1 内容结构

建议使用现有 `ModalDialog`，标题为「支持 WineStock」，内容保持短而直接：

```text
支持 WineStock

如果 WineStock 对你有帮助，欢迎通过下面的方式支持项目维护。

[微信二维码]       [支付宝二维码]
微信              支付宝

关闭                         稍后再说 / 不再提示
```

实际可用的支付方式以项目维护者最终提供的资料为准。若只有一种方式，不保留空的第二列；移动端改为单列，避免二维码缩小到无法扫描。

### 3.2 行为定义

- 「支持软件」：打开第一个有效捐赠方式，或在有多个方式时保持 Dialog 展示并由用户选择。
- 支付二维码只展示二维码，不提供二维码内容复制入口。
- 「关闭」或 Escape：视为暂不决定，进入较短冷却期，不永久关闭入口。
- 「稍后再说」：将当前里程碑标记为已处理，并进入 30 天冷却期。
- 「不再提示」：永久关闭自动提示，但不隐藏头像弹层中的「支持软件」入口。

「关闭」和「稍后再说」必须有清晰区别。关闭只代表当前不想处理，稍后再说代表用户明确接受未来提醒；无论哪种选择，当前里程碑都视为已处理，不会重复提示同一个里程碑。

### 3.3 视觉和响应式要求

- 复用当前主题 token、Dialog、按钮和二维码图片加载模式。
- 二维码放在不透明的浅色内容表面上，确保浅色和深色主题下均可扫描；不要对二维码应用透明度、滤镜或深色反转。
- 使用普通内容区和分隔线组织捐赠方式，不套嵌多层卡片，不使用渐变、装饰性插画或营销页式大标题。
- 每个二维码必须有可理解的替代文本，例如「微信捐赠二维码」。
- 桌面端验证 `1440 × 900`；断点附近验证约 `768px`；移动端验证 `390 × 844`。
- 移动端 Dialog 使用现有底部面板规则，二维码和操作按钮不能超出可视区域；内容较长时只允许 Dialog 内滚动，不产生页面横向滚动。

## 4. 提示控制器

### 4.1 目录建议

新增前端领域目录 `frontend/src/donation/`，职责拆分如下：

```text
frontend/src/donation/
  config.ts          # 支付方式、阈值和冷却时间
  storage.ts         # 版本化 localStorage 读写、校验和迁移
  controller.ts       # 纯计数与触发决策，不依赖 Vue 或 UI
  state.ts            # Dialog 开关和待处理提示事件的前端状态
  DonationDialog.vue # 统一永久入口和自动提示的 Dialog
  DonationDialog.scss
```

如果现有目录约定要求组件直接放在 `components/`，可以将 Dialog 放入 `components/donation/`，但计数和存储仍应留在独立的
`donation/` 领域，避免把业务页面状态塞入 `AccountPopover`。

### 4.2 控制器状态

建议使用版本化记录：

```ts
type DonationMilestone =
  "app-open-10" | "app-open-50" | "items-created-50" | "items-created-100" | "items-created-300";

type DonationPromptState = {
  version: 1;
  totalAppOpens: number;
  totalItemsCreated: number;
  reachedMilestonesAt: Partial<Record<DonationMilestone, string>>;
  acknowledgedMilestones: string[];
  promptCount: number;
  lastPromptAt: string | null;
  snoozeUntil: string | null;
  autoPromptDisabled: boolean;
};
```

存储键建议为 `winestock.donation-prompt.v1`。该记录是本机应用级偏好，不绑定某个登录用户；同一浏览器或设备上的不同账号共享累计计数，避免把捐赠功能接入账户数据。

里程碑 ID 建议固定为：

```text
app-open-10
app-open-50
items-created-50
items-created-100
items-created-300
```

控制器公开的最小操作：

```ts
recordAppOpen(): void;
recordItemsCreated(count: number): void;
evaluate(): DonationPromptDecision;
markPromptShown(milestone: DonationMilestone, now?: Date): void;
snooze(days: number): void;
disableAutoPrompt(): void;
```

控制器只返回决策，不直接操作 Dialog。例如：

```ts
type DonationPromptDecision =
  | { kind: "not-eligible" }
  | { kind: "cooldown" }
  | { kind: "disabled" }
  | {
      kind: "eligible";
      milestone: DonationMilestone;
      reason: "app-open" | "items-created";
    };
```

`evaluate()` 只返回当前队列中的一个里程碑。优先取最早达到且尚未处理的里程碑；若无法可靠判断达到时间，则按配置声明顺序处理。应用壳打开 Dialog 后立即调用 `markPromptShown`，把该里程碑加入 `acknowledgedMilestones`，从而保证重复事件不会重复提示。

### 4.3 记录方案

记录分为两层：`localStorage` 保存跨应用会话的累计总数，`sessionStorage` 保存当前应用会话的防重复标记。

```text
应用新会话进入有效 AppShell
        |
        v
sessionStorage 检查本会话是否已记录
        |
        v
未记录 -> donationController.recordAppOpen()
        |
        v
localStorage 累加 totalAppOpens 并检查打开里程碑

createItem() 的 POST 成功
        |
        v
donationController.recordItemsCreated(1)
        |
        v
localStorage 累加 totalItemsCreated；不检查、不发出提示
```

#### 软件打开次数

- 记录位置：`frontend/src/layouts/AppShell.vue` 的有效应用壳初始化阶段。
- 只有进入已登录应用壳或本机静默应用壳才计数；登录页、注册页、首次运行设置、运行设置页和服务不可用覆盖层不单独计数。
- 同一个前端运行会话只计 1 次。使用 `sessionStorage` 保存会话标记，避免路由切换、AppShell 重渲染或浏览器刷新重复计数。
- 用户关闭软件并重新启动，或关闭浏览器标签页后重新打开，视为新的应用会话；从后台恢复、切换路由和打开/关闭 Dialog 不计数。
- 记录成功后只在下一次有效应用启动时调用里程碑检查；如果 localStorage 不可用，应用仍正常运行，只是本机计数无法持久化。

#### 添加物品操作

- 记录位置：`frontend/src/api/items.ts` 的 `createItem()` 成功返回之后。
- 该函数是当前所有单项新建、扫码新建和批量新建调用的统一 `POST /api/items` 入口；在这里记录可以避免在多个页面重复埋点。
- 每次服务端确认创建成功的 `POST` 记录 `1` 件。物品编辑更新、删除、打开编辑器、保存草稿和仅加入入库/出库草稿均不计数。
- 批量创建逐件调用 `createItem()`，成功多少件就累计多少件；中途取消时只保留已经成功返回的数量。
- `sku_taken`、校验失败、图片上传失败、网络异常和用户取消不计数。批量流程将已存在物品匹配回来时，`created: false` 不再额外计数。
- 创建请求已经被服务端接受但响应在网络中丢失时，前端无法在不增加幂等 API 或查询比对的情况下确认事实；第一版采用“客户端确认成功才计数”的口径，不把不确定结果计入。
- 新增物品达到 50/100/300 件时只记录未处理里程碑，不在当前创建流程中弹窗；下一次有效启动才发出提示请求。

#### 持久化和并发

- 使用版本化键 `winestock.donation-prompt.v1` 保存累计数、已达到里程碑和冷却状态；每次事件都执行读取、校验、更新、写回。
- 控制器初始化时先读取最新 localStorage，非法记录回退默认值，不阻塞业务页面。
- 监听同源 `storage` 事件，在其它标签页更新后刷新内存快照；写入前重新读取，降低多标签页同时操作造成的计数覆盖。
- Desktop 和 Android 的主要场景是单一应用 WebView；多标签页/多浏览器窗口只作为 Web 运行模式支持。第一版不建立服务端计数，也不要求跨设备合并。
- 清除站点数据、卸载应用或更换浏览器配置文件会清空这些累计值，这是本机匿名偏好的正常结果。

### 4.4 开发环境启动测试参数

仅开发构建读取以下 URL 参数，生产构建会忽略它们：

| 参数                  | 含义                                     |
| --------------------- | ---------------------------------------- |
| `donation_test_opens` | 当前真实启动之外，额外模拟的累计启动次数 |
| `donation_test_items` | 当前启动前额外模拟的成功新增物品数量     |

示例：`/?donation_test_opens=9&donation_test_items=50#/dashboard` 表示在本次真实启动前模拟 9 次启动和 50 件新增物品，本次启动再计 1 次，并在启动空闲后检查提示。参数每次启动都会重新累加，适合连续验证 10/50 次启动和 50/100/300 件新增阈值。

测试前可以在浏览器控制台清除 `winestock.donation-prompt.v1` 和 `winestock.donation-open-recorded.v1`，避免已有本机累计数据影响结果。

### 4.5 计数语义

必须在「有效业务结果」发生后计数：

- 打开次数：应用壳完成一次有效进入后计数，不统计登录页、设置向导或单纯路由切换。
- 新增物品：HTTP 创建成功后计数；失败、取消、仅打开编辑 Dialog、保存草稿不计数。
- 批量导入或批量创建：按服务端实际成功创建的物品数量一次性增加；失败项和重复项不计数。
- 同一成功结果不得被多个页面重复上报。实施时应在 `frontend/src/api/items.ts` 的统一 `createItem()` 成功路径调用 `recordItemsCreated(1)`，页面和批量 composable 不再各自调用。
- `count` 小于等于 0、非有限数或异常大值应被忽略或限制，防止错误调用污染累计数。

### 4.6 触发和冷却状态机

```text
新增物品成功
          |
          v
     累加累计计数并记录里程碑
          |
          v
当前启动？ -- 否 --> 等待下一次应用启动
          |
         是（应用启动时）
          v
达到新的 10/50 次打开或 50/100/300 件新增里程碑？ -- 否 --> 不提示
          |
         是
          v
自动提示关闭或仍在冷却？ ----- 是 --> 保留未处理里程碑
          |
         否
          |
          v
取队列中的一个里程碑并发出 eligible 事件，应用壳空闲后打开 Dialog
          |
          v
记录该里程碑已处理并记录 lastPromptAt
```

建议冷却规则：

| 场景                     | 自动提示处理                              |
| ------------------------ | ----------------------------------------- |
| 首次达到任一里程碑       | 进入可提示状态；实际展示仍等待应用空闲    |
| 用户关闭 Dialog          | 14 天内不自动提示；当前里程碑标记为已处理 |
| 用户选择稍后再说         | 30 天内不自动提示；当前里程碑标记为已处理 |
| 用户选择不再提示         | 永久关闭自动提示；未处理里程碑不再消费    |
| 浏览器时间回拨或存储损坏 | 校验失败时回退默认状态，不阻塞应用        |

里程碑达到后即使处于冷却期也不能丢弃。它们保持在未处理状态，冷却结束后在下一次有效应用事件中继续检查；不能因为用户短时间内连续新增物品而连续弹出多个提示。所有 5 个里程碑处理完毕后，自动提示自然停止；只要 `donationEnabled` 仍为 true，永久入口继续保留。

### 4.7 初始化时机

- 控制器应在 AppShell 或应用启动装配层初始化一次。
- 控制器初始化前先读取 `donationEnabled`；配置未启用时直接进入 disabled 状态，不记录打开和新增物品事件。
- `recordAppOpen()` 放在已进入应用壳的生命周期中，不能放在登录页或每次路由进入钩子中。
- 自动提示事件不能在服务断连覆盖层、首次运行设置、强制改密或其它全屏流程中展示。
- 账户弹层和 Dialog 的开关状态必须独立；关闭账户弹层后再打开 Dialog，不能出现两个浮层同时可交互。
- 账户弹层、移动导航和捐赠 Dialog 都要遵循现有原生返回优先级和焦点恢复规则。

## 5. 捐赠内容与配置

### 5.1 环境变量驱动的二维码

采用 `zxing-wasm` 的 writer 子路径在运行时生成二维码，不提交微信或支付宝图片资源：

```ts
import { writeBarcode } from "zxing-wasm/writer";

const result = await writeBarcode(donationContent, {
  format: "QRCode",
  scale: 4,
  addQuietZones: false,
  addHRT: false,
  options: "ecLevel=H",
});

// 使用 result.image（PNG Blob）创建 object URL，绑定到 <img>。
```

Context7 当前文档确认 `writeBarcode()` 支持 `QRCode`，并返回 SVG、PNG Blob、UTF-8 字符串和原始像素数据。WineStock 现有 `zxing-wasm` reader 只负责扫码读取，writer 应单独懒加载：

- 读取路径继续使用 `zxing-wasm/reader`，不改现有扫码模块。
- 捐赠 Dialog 首次需要展示二维码时再动态导入 `zxing-wasm/writer`。
- 不使用 `zxing-wasm/full`，避免把 reader 和 writer WASM 合并到不需要的场景。
- `result.image` 生成的 object URL 在二维码内容变化和组件卸载时调用 `URL.revokeObjectURL`，避免重复打开 Dialog 造成 Blob URL 泄漏。
- 不使用 `v-html` 直接插入 SVG；优先使用 PNG Blob，避免把生成字符串当作 HTML 解释。

建议的公开构建变量：

```dotenv
VITE_DONATION_WECHAT_CONTENT=
VITE_DONATION_ALIPAY_CONTENT=
```

其中 `*_CONTENT` 是要编码进二维码的完整公开内容，可以是支付 URI 或公开赞助页面地址。变量声明同步写入 `frontend/src/env.d.ts`，示例键写入 `frontend/.env.example`，真实值只放在本机 `.env.local` 或发布构建环境中。

配置可用性统一按 `trim()` 后的非空字符串判断：

| 配置                                                         | 为空或不存在时                         |
| ------------------------------------------------------------ | -------------------------------------- |
| `VITE_DONATION_WECHAT_CONTENT`                               | 隐藏微信捐赠方式，不调用二维码生成器   |
| `VITE_DONATION_ALIPAY_CONTENT`                               | 隐藏支付宝捐赠方式，不调用二维码生成器 |
| 两个变量全部为空或不存在时，导出 `donationEnabled = false`： |

- 头像账户弹层不显示「支持 WineStock」入口。
- 自动提示控制器不记录里程碑、不执行冷却判断、不打开 Dialog。
- 不加载 `zxing-wasm/writer`，不生成二维码。
- 账户弹层和设置页不得留下空的捐赠分组或占位文字。

只要两个变量中至少有一个非空，`donationEnabled = true`，入口显示；Dialog 只展示已配置的捐赠方式。

该判断发生在构建后的前端配置层，发布包运行期间不会动态改变。若后续构建包补充或移除环境变量，随新构建结果生效。

### 5.2 配置边界和降级

- `VITE_*` 会在 Vite 构建时被替换并进入前端产物，绝不能放密钥、私有 token、后台凭据或任何需要保密的支付信息。
- 这类配置是“避免提交二维码文件”，不是运行时保密配置；用户仍可从构建产物中看到二维码内容。
- 环境变量为空时隐藏对应捐赠方式；如果所有方式为空，同时隐藏永久入口和自动提示，不渲染空的二维码区域。
- writer WASM 加载失败、编码失败或 WebView 不支持 Blob URL 时，只显示二维码暂时不可用的错误状态，并通过 Notice 告知用户；不暴露或复制二维码原始内容。
- 二维码必须黑色前景、白色不透明背景，不使用主题色、透明背景、滤镜或反色；生成器关闭内置 quiet zone，由二维码容器的白色内边距提供必要的识别缓冲。
- 捐赠内容变更需要重新构建前端；不在运行中请求远程配置，避免外部内容改变支付目标。
- Android 的 `build:android` 使用独立构建模式，发布流程必须显式向该构建注入 `VITE_DONATION_*`；不能假设普通 Web 的 `.env.local` 会自动进入 APK。
- 构建前应校验内容不是空字符串；不能把用户名、物品名称、计数或其它业务数据拼进二维码内容。

### 5.3 内容安全与隐私

- 二维码内容只在构建时注入前端，不向 core、遥测 SDK 或其它第三方服务发送。
- 不向 core、遥测 SDK 或第三方统计发送提示曝光、捐赠点击和支付信息。
- 若未来需要统计转化，必须另行获得明确同意并更新隐私说明，不作为本方案默认内容。

## 7. 测试矩阵

### 控制器纯逻辑测试

- 打开 9 次不提示，第 10 次达到 `app-open-10`。
- 打开达到 50 次时只触发一次 `app-open-50`，不会重复触发 `app-open-10`。
- 新增 49 件不提示，第 50 件达到 `items-created-50`。
- 从 50 件直接批量新增到 300 件时，`items-created-100` 和 `items-created-300` 均能被记录，但不会连续弹出多个 Dialog。
- 每个里程碑最多提示一次；提示展示后不会因同一累计总数重复提示。
- 冷却期间达到的新里程碑会排队，冷却结束后的下一次有效事件只提示一个。
- 关闭、稍后再说和不再提示分别产生正确冷却状态。
- 关闭自动提示后，永久头像入口仍可打开 Dialog。
- 批量新增只按成功数量计数，失败和取消不计数。
- 非法 JSON、旧版本、负数、无穷数和损坏日期回退到默认状态。
- 多次重复初始化不会重复记录同一次应用打开。
- 同一 AppShell 会话重复挂载或刷新页面不会重复记录打开；新应用会话只记录一次。
- `createItem()` 成功一次只增加 1 件；`updateItem()`、删除和草稿保存不增加数量。
- 批量创建只按真正成功的 `createItem()` 调用累计；已有匹配、失败、取消和 `sku_taken` 不增加数量。
- 创建请求成功但后续刷新列表失败时，仍保留已确认的新增计数，不因页面刷新失败回滚。
- 捐赠内容为空时不生成二维码；writer 加载或编码失败时显示错误状态。
- 两个捐赠变量全部为空或不存在时隐藏头像入口和自动提示；只配置其中一个时只显示对应内容。
- 重新打开 Dialog 或切换主题不会遗留旧 object URL；组件关闭和卸载后释放 Blob URL。

### UI 和交互验收

- 头像菜单可用键盘打开、关闭和聚焦到「支持 WineStock」。
- 从头像菜单进入 Dialog 后，账户菜单已关闭，关闭后焦点回到头像按钮。
- Dialog 内二维码有替代文本，按钮有明确名称，Escape 和原生返回可关闭。
- 自动提示不会覆盖新增成功反馈、保存中的表单、登录、首次设置或服务断连层。
- `1440 × 900`、约 `768px` 和 `390 × 844` 下无横向溢出、按钮文字裁切或二维码不可扫描。
- 浅色和深色主题都满足对比度和二维码可读性要求。
- 浏览器控制台无新增 error、warning 或未处理 Promise rejection。

## 8. 实施前需确认的事项

以下内容在写代码前必须由项目维护者确认：

1. 实际支持哪些方式：微信、支付宝或其它二维码内容。
2. 是否提供一张统一二维码，还是按方式提供多张二维码。
3. 是否确认采用五个累计里程碑：打开 10/50 次，新增 50/100/300 件；可在代码中保留配置常量。
4. 「关闭」是否单独保留 14 天冷却，还是只保留「稍后再说」和「不再提示」。
5. 项目名称和 Dialog 文案是否使用「支持 WineStock」这一表述。

## 9. 推荐结论

采用「头像弹层永久入口 + 统一捐赠 Dialog + 本机前端控制器」的方案。第一版不改后端，不新增依赖，不采集捐赠数据，按累计打开 10/50 次、成功新增 50/100/300 件物品的五个里程碑逐级提示。每个里程碑只处理一次，并用 14/30 天冷却和「不再提示」控制打扰频率；所有二维码变量为空时整个捐赠功能关闭，至少有一个变量有效时才显示入口和对应内容。

该方案保留了项目后续调整空间：可以替换支付方式、二维码和阈值，而不改变应用壳、业务 API 或数据库边界。
