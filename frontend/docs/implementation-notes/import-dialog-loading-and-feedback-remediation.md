# 导入 Dialog 一次性加载与异步反馈整改方案

## 1. 背景与目标

入库工作台的“导入订单”和“导入 ERP 备份”目前可以正常解析文件，但选择文件后，器件匹配结果会逐行到达、逐行改写预览表。数据量稍大时，列表持续重排，用户需要等待并观察一个不断变化的滚动区域；同时部分后台请求没有任何可见状态，失败也被静默吞掉，用户无法判断当前是在匹配、检查、准备库位还是已经卡住。

本方案的目标：

- 文件解析完成后，一次性取得本批器件的本地物品匹配结果，再一次性提交到预览状态；
- 导入 Dialog 始终显示当前阶段、进度和可操作结果，不让后台请求静默发生；
- 保留逐行的最终结果、失败原因和重试能力，但不再让逐行网络响应驱动界面刷新；
- 导入预览不使用分页或触底加载语义，列表只在数据准备完成后完整呈现；
- 统一订单导入与 ERP 备份导入的异步状态、取消、重试和错误呈现规则。

阶段一已落地，阶段二的核心反馈和错误恢复也已随本次改动实现；本文件同时作为实现记录和后续验收基线。

当前实现摘要：

- Core 新增 `POST /api/items/options/lookup`，按 SKU 精确批量查询并返回未命中结果；前端超过 500 个客编时自动分块，但在 Dialog 中仍作为一个批次呈现。
- 订单导入与 ERP 备份导入在匹配响应完成后一次性替换行状态，增加匹配计数、失败提示、重试和文件解析竞态保护。
- ERP 的重复导入检查、库位统计失败不再静默转为安全值，而是阻止确认并提供重试入口。
- 批量创建开始前再次校验本地 SKU；已存在物品直接回填，只有确认未命中的客编才进入立创资料和创建流程。
- 批量创建按客编串行执行“查询立创资料 -> 创建物品”，每个客编查询完成后立即进入创建，并在按钮和行状态中显示当前阶段与总进度。
- ERP 确认导入显示查询库位、准备库位和组装库存阶段；库位准备失败保留错误并提供重试，执行期间禁止关闭 Dialog。

## 2. 现状盘点

### 2.1 订单导入

`LcscOrderImportDialog.vue` 当前流程：

```text
选择文件
  -> parseLcscOrderFile
  -> 创建 rows，所有可匹配行标记 matching
  -> matchPendingRows
       -> 最多 4 个 worker
       -> 每个 worker 逐行调用 GET /api/items/options?search=C...
       -> 每个响应直接改写该行 status/item/reason
  -> 用户继续操作
```

对应实现位置：

- 文件解析状态：`frontend/src/components/stock-draft/LcscOrderImportDialog.vue:322`
- 逐行匹配队列：`LcscOrderImportDialog.vue:381`
- 单行请求和状态写入：`LcscOrderImportDialog.vue:395`
- 表格直接渲染每一行状态：`LcscOrderImportDialog.vue:71`

当前已经有 `matching` 状态和操作区“正在匹配…”，但只有按钮文案是批次级反馈，表格仍会随着四个 worker 的返回顺序逐行变化；没有“已完成/总数”、失败数量和当前阶段的稳定摘要。

### 2.2 ERP 备份导入

`ErpBackupImportDialog.vue` 当前流程：

```text
选择文件
  -> parseErpBackupFile
  -> 创建 componentRows，所有器件标记 matching
  -> Promise.all(
       matchComponents: 4 个 worker 逐行查询本地物品
       computeNewLocationCount: 查询库位并计算待新建数量
       checkDuplicate: 查询是否存在同文件名入库单
     )
  -> 用户继续操作
```

对应实现位置：

- 文件解析和行模型创建：`frontend/src/components/stock-draft/ErpBackupImportDialog.vue:300`
- 并行准备任务：`ErpBackupImportDialog.vue:328`
- 逐行本地匹配：`ErpBackupImportDialog.vue:345`
- 重复导入检查失败被静默转为 `false`：`ErpBackupImportDialog.vue:331`
- 待新建库位统计失败被静默转为 `0`：`ErpBackupImportDialog.vue:377`
- 确认时逐个串行创建库位：`ErpBackupImportDialog.vue:467`

ERP Dialog 的表格也没有触底加载哨兵；问题不是分页本身，而是每个请求完成都会让表格行状态和高度逐步变化。`overflow: auto` 的预览容器（约 300px）放大了这种“列表还在滚动/还没稳定”的感受。

### 2.3 当前静默操作

| 操作 | 当前反馈 | 问题 |
| --- | --- | --- |
| 解析订单/备份文件 | 有“正在解析…” | 缺少文件读取阶段和结果数量摘要 |
| 本地物品匹配 | 行内“匹配中…”；订单按钮改为“正在匹配…” | 无进度计数；逐行响应导致列表持续变动 |
| ERP 重复导入检查 | 无 | 失败时用户不知道检查未完成 |
| ERP 待新建库位统计 | 无 | 失败静默显示待新建 0 个，可能误导用户 |
| 批量创建元数据加载 | 子 Dialog 内部分反馈 | 父 Dialog 没有统一阶段说明 |
| 立创批量查询、图片、上传、建档 | 主要显示行状态或底部按钮 | 查询与创建阶段没有总进度；失败范围不清楚 |
| ERP 确认时库位查询/新建 | 只显示“正在导入…” | 无法区分查询库位、创建库位和组装草稿 |
| 重试 | 订单有“重试匹配”，ERP 没有匹配重试入口 | 两个 Dialog 的失败恢复能力不一致 |

## 3. 目标状态模型

两个导入 Dialog 共用同一批次级状态语义，具体文案可以按业务替换：

```text
idle
  -> parsing
  -> preparing
  -> matching
  -> ready
  -> importing
  -> completed

任意阶段 -> failed（保留已有解析/预览结果）
任意可取消阶段 -> cancelled（清理本次未完成任务，不清空可恢复预览）
```

建议状态字段：

```ts
type ImportStage =
  | "idle"
  | "parsing"
  | "preparing"
  | "matching"
  | "ready"
  | "importing"
  | "completed"
  | "failed"
  | "cancelled";

interface ImportProgress {
  stage: ImportStage;
  completed: number;
  total: number;
  message: string;
  error: string;
}
```

行状态继续保留 `matched`、`missing`、`failed`、`creating` 等业务结果，但不再用每个 HTTP 响应直接驱动 DOM 增量重排。匹配请求结束后，在一次状态提交中完成：

```text
请求开始：显示批次级 matching + 进度
请求成功：按 product_code 建索引，一次性更新全部行
请求失败：保留原始行，批次级显示失败和重试；不把未完成行伪装成 missing
```

## 4. 一次性本地匹配方案

### 4.1 推荐：新增 Core 批量本地匹配接口

现有 `GET /api/items/options` 是面向搜索选择器的分页接口，不适合作为导入批次的逐行查询接口。建议新增：

```text
POST /api/items/options/lookup
```

请求：

```json
{
  "product_codes": ["C123", "C456"]
}
```

响应按去重后的输入顺序返回每个客编：

```json
{
  "results": [
    { "product_code": "C123", "item": { "id": 1, "sku": "C123" }, "error": null },
    { "product_code": "C456", "item": null, "error": "not_found" }
  ]
}
```

Core 侧规则：

- 规范化并去重客编，保持输入顺序；
- 使用一次数据库 `IN` 查询，按 SKU 精确匹配，不走模糊搜索；
- 返回轻量 `ItemOptionResponse`，不加载库存详情、图片内容或物品编辑资料；
- 单次请求设置明确上限（建议 500，需结合 SQLite 参数上限和实际导入规模确认）；
- 复用现有物品选择权限，不扩大导入 Dialog 的授权范围；
- 单个客编不存在是结果项，不是整批 HTTP 错误；数据库错误才返回请求级错误；
- 修改 Core HTTP 契约后必须同步 OpenAPI 和前端生成类型。

前端在一个文件批次内只发起一次匹配请求。超过接口上限时，内部按固定块请求，但仍只显示一个连续的“匹配器件 x/y”阶段，不逐行展示网络加载，也不使用触底分页。

### 4.2 不推荐：加载整个物品选项列表后前端匹配

将 `GET /api/items/options?search=&page_size=200` 作为一次性加载方案会：

- 受 200 条分页上限影响，无法保证覆盖全部本地物品；
- 把与本次导入无关的物品全部传到前端；
- 仍需要处理大列表分页，重新引入滚动或隐式分页语义；
- 在权限、网络和内存方面都比按客编精确查询更差。

因此不作为正式方案。

## 5. 两个 Dialog 的目标流程

### 5.1 订单导入

```text
选择文件
  -> 正在解析订单表格
  -> 解析完成：一次性展示行数/去重数/跳过数
  -> 正在匹配本地物品 0/N
  -> 一次性写入全部 matched/missing/failed 行状态
  -> ready：显示匹配数、未命中数、失败数和可创建数
```

匹配失败时：

- 批次级提示“部分匹配失败”，显示失败数量和“重试失败项”；
- 失败行保留 `failed`，不得直接变成 `missing`；
- 重试只发送失败客编，成功行保持原结果；
- 批次请求失败时提供“重试匹配”，不阻塞用户查看已解析的订单信息。

### 5.2 ERP 备份导入

```text
选择文件
  -> 正在解析备份
  -> 正在准备导入摘要：检查重复导入、读取现有库位
  -> 正在匹配本地物品 0/N
  -> 一次性更新全部器件状态
  -> ready：显示库位、待新建库位、器件匹配、待创建和库存行摘要
```

重复检查和库位读取可以并行，但必须各自拥有可见状态：

- 重复检查成功：显示“未发现同来源入库单”或警告详情；
- 重复检查失败：显示“无法确认是否重复导入”，提供重试，并默认阻止最终导入；
- 库位读取失败：显示错误和重试，不得把待新建数量静默改成 0；
- 物品匹配失败：只影响匹配结果，不掩盖重复检查和库位检查状态。

确认导入阶段继续拆成可见步骤：

```text
正在准备库位 0/M
  -> 正在组装期初库存 0/K
  -> 已准备导入草稿
  -> 由父工作台显示提交结果
```

缺失库位较多时，优先增加 Core 批量解析/创建接口；若暂时保留逐条创建，至少使用有界并发、进度计数和失败列表，不能只显示笼统的“正在导入”。

## 6. 界面反馈整改

### 6.1 Dialog 顶部批次状态条

在文件行和摘要之间增加稳定高度的状态区域，使用 `role="status"`、`aria-live="polite"` 和 `aria-busy`：

```text
正在解析订单表格…
正在匹配本地物品 18/126…
匹配完成：已匹配 102，未命中 20，失败 4
正在检查备份是否重复导入…
正在准备库位 3/12…
```

状态条出现和消失不能改变表格起点；按现有异步规范使用稳定等待呈现，短于 200ms 的状态不闪烁。

### 6.2 操作区规则

- `parsing`、`preparing`、`matching` 时禁止重新选择文件，避免旧请求覆盖新文件；提供明确“取消准备”或关闭即取消；
- `ready` 时显示重试失败项、批量创建和确认导入；
- `importing` 时禁止关闭和重复提交，按钮显示当前阶段与进度；
- 失败时保留预览和已成功结果，不把整个 Dialog 退回空白；
- 普通导入按钮的禁用必须有原因提示，不能只呈现灰色按钮；
- 成功加入草稿/完成导入使用 Notice；单纯选中或匹配完成使用信息型状态，不使用成功色替代状态语义。

### 6.3 预览表与滚动

- 预览表是一次性数据视图，不增加“继续向下滚动加载”文案或分页哨兵；
- 表格容器可以继续使用有限高度和自然滚动，但容器高度、表头位置和状态条位置必须稳定；
- 匹配期间可以先显示固定行骨架，匹配完成后一次性替换为最终行状态；
- 数据量超过实际渲染阈值后再评估虚拟列表，不能为了避免刷新而引入新的分页语义；
- 桌面、约 768px 和 390px 视口都检查 Dialog 内容区是否发生横向溢出，最后一行可滚动到固定操作区上方。

## 7. 取消、竞态与错误边界

当前 `handleFileChange` 没有独立的文件解析请求代次；用户快速连续选择文件时，旧文件解析完成后可能覆盖新文件。整改时增加 `runId` 或文件级 `AbortController`：

```text
每次选择文件生成 runId
解析、匹配、准备任务都携带 runId
只有当前 runId 能提交状态
选择新文件/关闭 Dialog 时取消旧任务
```

错误分层：

- 文件格式错误：文件级错误，允许重新选择；
- 本地匹配部分失败：结果项错误，允许只重试失败客编；
- 重复检查/库位读取失败：准备阶段错误，提供重试，必要时阻止导入；
- 建库位或组装失败：导入阶段错误，保留已完成数量和失败对象，避免重复创建；
- 用户取消：不显示错误 Notice，不把取消误报为网络失败。

## 8. 分阶段实施

### 阶段一：一次性匹配与稳定列表

1. 增加 Core 批量本地物品匹配接口和 OpenAPI 类型。
2. 两个 Dialog 去掉 4 worker 逐行 `listItemOptions`，改为批量请求。
3. 请求完成后一次性应用匹配结果，增加匹配进度、失败数量和失败重试。
4. 增加文件选择代次，阻止旧文件结果覆盖新文件。
5. 保留表格自然滚动，但删除任何分页/继续滚动加载语义。

### 阶段二：异步操作可见化

1. 抽取两个 Dialog 共用的导入阶段状态模型和进度展示。
2. 为 ERP 的重复检查、现有库位读取、待新建库位统计增加独立状态和重试。
3. 为订单/ERP 的文件解析、物品匹配、批量创建统一文案和 `aria-busy`。
4. 按现有 `async-state-transitions.md` 复用延迟显示、最短展示和旧结果保留规则。

### 阶段三：导入执行可追踪

1. 将库位准备和库存组装拆成有进度的步骤。
2. 评估 Core 批量库位解析/创建接口，减少逐条写入和中途部分成功。
3. 对部分成功、重复导入和取消恢复做专项验收，补齐审计/Notice 文案。

## 9. 测试与验收

### 逻辑与 API

- 批量匹配请求去重、规范化、保持输入顺序；
- 已有、缺失、数据库错误和部分失败结果映射正确；
- 超过批量上限时按约定分块或显示明确错误；
- 重试只包含失败客编；
- 旧文件解析完成后不能覆盖新文件；取消后不能写入状态；
- OpenAPI、生成类型和前端 API client 同步。

### 浏览器与 Dialog

- 1、30、200 个器件的订单和备份样本；
- 匹配延迟、部分失败、服务断开、重复检查失败、库位读取失败；
- 快速连续选择两个文件；匹配中关闭 Dialog；导入中尝试关闭/重复提交；
- 1440×900、接近 768px、390×844 检查状态条、表格高度、滚动位置和操作区；
- 控制台无新增错误或警告，状态条不闪烁，表格不因逐行响应跳动；
- `pnpm build`、相关 Node 单测、Core 批量接口测试和 `git diff --check` 通过。

## 10. 非目标

- 不改变订单字段、ERP 备份语义、C0 手工器件跳过规则和入库草稿契约；
- 不把导入预览改造成普通目录分页器；
- 不在前端加载全部物品目录替代精确批量匹配；
- 不把所有后台任务合并成无法解释的单一全屏 loading；每个用户可感知阶段仍需有明确文案和失败边界。
