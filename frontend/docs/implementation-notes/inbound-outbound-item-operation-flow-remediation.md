# 出入库“选择物品即配置明细”工作流整改方案

> 方案状态：已实施（前端工作流与视觉整改已落地）
> 2026-07-26 更新：入库模板与收货属性（ext_attributes）已整体移除，本文涉及入库模板/推荐链的章节仅作历史记录。
> 适用范围：/inbound 新建入库、/outbound 新建出库
> 不包含：入库单/出库单查询、审批工作台、库存扣减算法、Shell Bridge 和运行模式

## 1. 结论

当前页面把“选择物品”和“填写该物品的出入库参数”拆成两个完整步骤，不符合仓库操作的自然顺序。用户在第一步选择的是一组物品，第二步才重新识别每一行并补齐数量、库位、批次或分配方式；物品多时，用户需要反复在“我选了什么”和“这一行要怎么处理”之间切换。

整改目标不是把所有字段永久铺在目录中，而是把工作流改为：

```
搜索物品
  -> 添加并立即配置这一条明细
  -> 完成明细并继续添加
  -> 在明细列表复核
  -> 提交整张单据
```

核心原则：

- 物品选择和该物品的操作参数是一个连续动作。
- 来源/去向、备注等单据级信息只填写一次；数量、库位、批次、模板等明细级信息在对应物品编辑会话中完成。
- 选中物品只是创建本地草稿，不代表已经入库、出库或扣减库存。
- 关闭编辑器不丢失已填写的本地草稿；删除明细必须通过明确的移除操作。
- 保留现有 HTTP 契约、权限边界、草稿本地保存和 core 的最终校验。

## 2. 项目现状与问题证据

### 2.1 入库页面

当前实现位于 `frontend/src/pages/InboundDraftPage.vue`、
`components/inbound/InboundDraftStep.vue`、`InboundLineEditor.vue` 和共享的
`components/items/ItemSelectionDialog.vue`：

1. 页面只有一个稳定工作台；选择弹窗一次只提交一项物品。
2. 选择弹窗离场完成后立即打开该物品的完整入库明细编辑器。
3. 数量、单价、库位、批次、有效期、模板和动态属性都在同一编辑会话中完成。
4. 明细复核列表只读展示摘要，编辑与移除使用全站统一的图标按钮。
5. 恢复草稿只恢复明细数据，不恢复短生命周期的选择弹窗或编辑器。
6. 存在未完成明细时再次点击“添加物品”，直接返回该明细并显示 Warning Notice，不进入选品。

原 `InboundCatalogStep.vue` 已删除，步骤状态和“回到选品步骤”的业务语义不再存在。

### 2.2 出库页面

当前实现位于 `frontend/src/pages/OutboundDraftPage.vue`：

1. 目录选择一项物品后关闭选择层，并打开“配置出库明细” Dialog。
2. 数量、FIFO/指定批次、库位限制、批次候选和成本提示集中在该 Dialog。
3. 完成当前明细后，等待 Dialog 离场再打开下一次选择；未完成时再次点击“添加物品”，会返回该明细并显示 Warning Notice。
4. 明细复核列表只显示物品身份、操作摘要、成本提示和编辑/移除图标。
5. 选择控件、单选状态和列表按钮均复用项目现有视觉语言，不再使用原生蓝色选择控件。

出库不再维护 `step = catalog | draft`，Android 原生返回按最上层 Dialog/页面路由处理。

### 2.3 现有模型已经具备按明细配置的基础

前端草稿和 core 请求已经是明细行模型，不需要为了本次交互重做业务 API：

| 领域 | 单据级字段                     | 明细级字段                                                                                   | 当前请求           |
| ---- | ------------------------------ | -------------------------------------------------------------------------------------------- | ------------------ |
| 入库 | source、notes、submission_mode | quantity、unit_price、location_id、batch_no、expires_at、inbound_template_id、ext_attributes | POST /api/inbound  |
| 出库 | destination、notes             | quantity、batch_id、location_id                                                              | POST /api/outbound |

core/src/stock/service/inbound.rs 和 outbound.rs 都逐条校验并保存明细；服务端最终校验仍是权威来源。整改的第一版不增加“操作类型”字段，也不让 Shell Bridge 介入业务请求。

### 2.4 当前实现中的附带风险

这些问题不应被新交互掩盖，实施前要明确处理方式：

- 入库 core 允许同一物品在一张单据中出现多条明细（例如不同批次/库位），但前端 addItem() 和恢复逻辑当前按物品 ID 去重。第一阶段不要让目录加号静默产生重复行；如需要同物品多批次，应增加明确的“复制为另一条明细”动作。
- frontend/docs/page-outbound.md 描述创建页只形成待审批出库单，但当前 OutboundDraftPage.vue 在具备审批权限时会继续调用 approveOutboundOrder()。这属于既有业务决策不一致，不能因本次 UI 重构而默默改变；实施前应决定以文档/core 契约还是现有直接出库行为为准，并同步代码、文档和测试。
- 入库模板推荐、模板候选、出库批次和成本预估都存在异步请求。编辑器打开后不能假定这些数据已经完成，也不能用一个全局 loading 覆盖整张草稿。

## 3. 目标信息架构

取消“选品步骤/填写步骤”的业务分段，保留一个稳定的“新建入库/新建出库”工作台。页面结构如下：

```
页面标题 + 单据摘要
├─ 单据基本信息
│  ├─ 入库来源 / 出库去向（必填）
│  └─ 备注（可选，按需展开）
├─ 添加物品
│  ├─ SearchField
│  ├─ 服务端搜索、触底追加、错误重试
│  └─ 添加并配置 / 继续配置 / 编辑明细
├─ 已添加明细
│  ├─ 物品身份与本次操作摘要
│  ├─ 仅显示实际阻塞状态
│  └─ 编辑明细 / 移除明细
└─ 固定操作区
   ├─ 清空草稿
   └─ 提交审核 / 直接入库（按既有业务规则）
```

桌面端保持目录和明细列表的连续工作区；编辑单条明细时使用现有通用 ModalDialog，背景列表仍可见。移动端使用同一业务状态的底部面板和安全区感知的固定底部操作区，不维护第二套业务逻辑。

### 3.1 选择物品后的标准动作

目录按钮不再使用“已选时点击即移除”的 toggle 语义，避免误触删除已经配置好的明细：

| 物品状态         | 目录动作   | 结果                               |
| ---------------- | ---------- | ---------------------------------- |
| 尚未加入         | 添加并配置 | 创建默认明细并立即打开该明细编辑器 |
| 已加入且有阻塞项 | 继续配置   | 打开同一条明细并定位第一个阻塞字段 |
| 已加入且可提交   | 继续配置   | 打开同一条明细进行复核             |

移除只在“已添加明细”列表中提供，使用明确的移除图标和可访问名称。加入/移除仍可发信息型 Notice，但不把本地草稿选择显示为业务成功。

选择后创建的明细立即写入本地草稿并打开编辑器。用户关闭、按 Escape 或使用 Android 返回时保留当前已填写值；如果不想保留，使用“移除明细”。这样中断操作不会导致已经输入的批次、图片或属性丢失。

### 3.2 明细编辑器

编辑器标题使用任务语义，物品名称、SKU 和单位作为上下文：

- 入库：入库物品明细
- 出库：配置出库明细

编辑器底部只处理本地明细会话，不直接调用创建接口：

- 暂存并关闭：关闭编辑器并保留当前明细值。
- 完成并继续添加：校验当前明细后关闭编辑器，并把焦点交给下一次物品选择。
- 移除明细：从草稿删除；如存在未绑定入库图片，继续沿用现有资源清理逻辑。

“提交审核”“直接入库”仍是页面级主操作，不能让“完成明细”使用同等的业务成功语义。

### 3.3 入库明细字段顺序

InboundLineEditor.vue 已从原“批次与属性”侧栏扩展为通用 Dialog 内的完整明细编辑器，字段顺序为：

1. 数量。
2. 单价。
3. 入库库位。
4. 批次号。
5. 有效期。
6. 入库模板方案。
7. 模板动态字段和图片属性。

来源、备注仍属于单据级字段，放在工作台基本信息区，不在每一条明细重复。

推荐模板的解析可以在编辑器打开期间继续进行。模板正在加载、失效或候选读取失败时，编辑器和明细摘要显示同一原因；请求版本、模板切换确认、图片上传和恢复规则继续沿用现有入库模板整改方案。

### 3.4 出库明细字段顺序

新增 OutboundLineEditor.vue（或从当前页面抽取等价组件），把当前分散在行内和弹窗中的字段合并：

1. 数量。
2. 扣减方式：FIFO / 指定批次。
3. FIFO 的可选库位范围，或指定批次的分页候选。
4. 当前批次快照和成本预估说明。

数量和扣减方式必须在同一编辑会话中完成。批次余额仍只是读取快照，不能在界面上承诺审批时一定成功；库存充足性仍由审批事务判断。

### 3.5 明细列表的职责

明细列表改为“复核列表”，不再同时承担第二套编辑表单：

- 展示物品身份、数量和关键操作摘要。
- 入库显示库位、批次/有效期、模板摘要和金额小计。
- 出库显示数量、FIFO/批次/库位摘要和成本提示。
- 只显示缺失、失效、加载失败等实际阻塞；完成状态不再常驻渲染重复的“已配置”标签。
- 所有字段编辑通过对应编辑器完成，避免用户再次在宽表格中寻找同一物品。

顶部摘要可显示“明细总数”和“待配置数”。混合单位不伪造总量；入库单价或出库成本未具备可靠依据时不展示误导性的汇总金额。

## 4. 前端状态模型整改

### 4.1 页面状态

删除 currentStep/step 作为业务状态，以及 winestock.inbound.step 等步骤恢复逻辑。改为一个短生命周期的编辑器会话：

```
type DraftEditorOrigin = "catalog-add" | "review-edit" | "error-focus";

interface ActiveLineEditor {
  lineId: string;
  origin: DraftEditorOrigin;
}
```

activeLineEditor 不写入 localStorage 或 sessionStorage。应用刷新后只恢复草稿明细列表，用户可以从“继续配置”重新打开未完成明细。

### 4.2 明细状态

不要新增必须持久化的 ready 布尔值；从现有领域模型派生状态，避免保存后状态过期：

- 入库继续使用 lineReady()、模板状态和字段错误派生 incomplete/ready/error。
- 出库继续使用 lineError()，额外把批次候选加载失败和批次已失效作为可定位错误。
- 页面只保存真实业务值；编辑器是否打开、焦点位置、加载指示器属于瞬态。

新增物品后，即使用户尚未填写完整，也保留这条明细并显示实际阻塞原因（出库显示“待配置”，入库按字段显示首个阻塞）。提交时仍由现有字段校验阻止请求，并自动打开对应明细编辑器。

### 4.3 异步请求边界

- 入库每条明细的推荐模板/模板详情继续使用独立 AbortController 和请求版本；删除明细时取消请求。
- 出库每条明细的成本快照可以在输入数量后后台加载；编辑器关闭不应清除可复用快照，删除明细或切换物品时再取消。
- 指定批次候选只属于当前编辑器会话；关闭编辑器时取消当前候选请求，重新打开从当前批次页状态安全恢复或重新读取。
- 搜索、目录分页、模板候选和批次候选的主动取消不得显示错误或触发服务断连状态。
- 所有异步提示遵守 frontend/docs/async-state-transitions.md 的 200ms 延迟和 350ms 最短展示规则，不用延迟请求本身。

### 4.4 错误定位

提交错误仍通过后端 line_index 映射到 lineId，然后：

1. 保留其它明细和草稿。
2. 打开对应明细编辑器。
3. 聚焦字段或重试控件。
4. 在列表摘要保留持续错误状态。

移除步骤状态后，不得再通过“先回到填写步骤”实现错误定位。

## 6. 草稿与兼容策略

1. 继续使用现有入库 winestock.inbound-draft.v5 和出库 winestock.outbound-draft.v1。
2. 恢复旧草稿后直接进入统一工作台的明细复核状态，不自动打开任意明细编辑器。
3. 不再写入或读取步骤键；旧版本草稿只按现有字段恢复到复核列表。
4. 只要序列化字段不变，就不升级草稿版本；状态、编辑器来源和加载状态全部运行时派生。
5. 入库图片 IndexedDB、未绑定文件删除、模板恢复和提交成功后的清理逻辑保持不变。
6. 清空草稿、提交成功、确认离开和浏览器关闭保护继续使用现有统一流程。
7. 如果后续支持“同一物品复制为多条入库明细”，必须为 lineId、图片引用和模板字段定义明确迁移及重复清理规则，不能只关闭前端去重。

## 7. 权限、HTTP 与 core 边界

### 7.1 第一阶段不改 API

现有接口已经支持目标交互：

- POST /api/inbound 接收每条入库明细的完整字段。
- POST /api/outbound 接收每条出库明细的数量、批次和库位。
- 物品选项、库位、模板、批次和图片接口继续按既有权限调用。

实现前仍须依照项目检查清单先核对运行服务的 /api-docs/openapi.json，再核对 core/docs/business-api/；不得因为前端当前没有在某一步调用接口，就推断接口不存在。

### 7.2 权限保持

- 入库创建权限继续允许读取入库任务所需的活动模板；模板管理写权限不随页面开放。
- 出库创建、物品/批次读取、库位读取和审批权限仍按 core 实时授权，前端只收敛入口。
- 远端模式、Android/桌面 Shell、鉴权 token 和 API 地址不在本整改中变更。

### 7.3 直接生效语义

入库 pending_approval/direct 的现有语义继续由 core 响应决定。出库页面当前存在“文档描述 pending-only、实现按审批权限直接 approve”的差异，必须在 Phase 0 形成明确决策：

- 推荐方案：遵循 page-outbound.md 和 core 创建接口的 pending-only 语义，审批动作只在审批工作台发生；
- 若产品明确需要直接出库，则同步更新页面文档、路由说明、成功/失败文案和测试矩阵。

本次工作流重构不得借机修改库存扣减、审批事务或批次 FIFO 算法。

## 8. 分阶段实施计划

### Phase 0：决策冻结与基线（已完成）

- 确认出库是否允许创建后直接审批。
- 确认入库同一物品多批次是否需要首版支持；推荐先保留唯一选择，新增明确“复制明细”作为后续能力。
- 固定现有 OpenAPI、权限、草稿样例和三档视口截图作为回归基线。
- 记录当前页面的网络请求、错误映射和 Android 返回行为。

退出条件：业务语义、重复明细策略和验收数据已写入页面文档，无未决的 API/权限假设。

### Phase 1：统一工作台骨架（已完成）

- 去掉两页的业务步骤状态、步骤恢复和 PageState 返回。
- 建立添加区、单据基本信息区、明细复核区和固定提交区。
- 将目录动作改为添加/继续配置/编辑，不再通过选中 toggle 删除。
- 建立 activeLineEditor 和编辑器关闭后的焦点回收。
- 不移动领域字段，不改请求契约，先让“选择后立即打开现有编辑器”可用。

退出条件：可连续添加多个物品；每次添加都打开对应编辑器；关闭后明细仍保留；提交仍生成原请求结构。

### Phase 2：出库明细一体化（已完成）

- 在 `OutboundDraftPage.vue` 中建立等价的单条明细 Dialog；暂不额外拆分组件，避免只为对称而增加层级。
- 将数量从复核行移入编辑器，与 FIFO/指定批次和库位/批次选择同屏。
- 保留批次分页、成本预估、库存快照警告和取消请求。
- 明细列表只显示数量与分配摘要。

退出条件：用户从目录选中一个物品后，只需在一个编辑会话内完成数量和扣减方式；FIFO、指定批次、库位限制和批次候选失败均可恢复。

### Phase 3：入库明细一体化（已完成）

- 扩展 InboundLineEditor，收纳数量、单价、库位、批次、有效期、模板和动态字段。
- 保留推荐模板状态、失效模板处理、模板切换确认、图片资源清理和后端字段定位。
- 明细复核行只展示身份、数量/金额、库位、批次和模板摘要。
- 把“完成并继续添加”接到模板/图片编辑器完成后的搜索焦点。

退出条件：用户不需要回到另一张表格补数量/单价/库位；模板加载、图片选择和错误修复不丢失明细草稿。

### Phase 4：清理与文档同步（本轮完成）

- 删除无调用的步骤组件、步骤 SCSS、过时注释和重复文案。
- 同步 `page-inbound.md`、`page-outbound.md`、`routes.md`、`mobile-interactions.md`、前端代码地图和 README。
- 复用 `ItemSelectionDialog`、`ModalDialog`、`SelectControl`、统一 icon-button、motion 和 safe-area token。
- 用真实浏览器检查桌面、断点附近和移动视口的列宽、溢出、浮层串行和控制台状态。

退出条件：文档不再描述已经删除的“两步选品/填写”交互，代码地图与实际职责一致。

## 9. 验收矩阵

### 9.1 业务流程

- 选择一个入库物品后自动打开完整入库明细编辑器。
- 选择一个出库物品后自动打开包含数量和扣减方式的出库明细编辑器。
- 完成一条明细后能直接继续添加下一条，不必重新进入第二步骤。
- 编辑已添加明细不会清空其它明细；移除只通过明确移除动作。
- 单据级来源/去向和备注只保存一次，能在任意明细编辑前后修改。
- 提交前缺少字段时，页面打开对应明细并聚焦首个错误。
- 入库 pending/direct 和出库 pending/直接生效的最终语义与 Phase 0 决策一致。

### 9.2 入库专项

- 数量、单价、库位、批次号、有效期、模板和动态属性都能在同一编辑会话完成。
- 推荐模板成功、待填、失效、候选权限失败、网络失败和迟到响应均有稳定状态。
- 模板切换确认仍能保护字段值和图片；取消后原值完全保留。
- 新建明细、恢复草稿、移除明细和清空草稿不会留下未绑定文件或错误图片预览。
- 同一物品是否允许多条明细按 Phase 0 决策验收，不能出现静默重复或静默合并。

### 9.3 出库专项

- 数量、FIFO/指定批次、库位限制在同一编辑会话完成。
- 批次分页、无批次、403、网络失败、批次失效和成本预估不足均可重试或安全降级。
- 当前批次余额只作为提示，不显示“已锁定”或“审批必然成功”。
- 提交请求的 batch_id/location_id 与编辑器最终状态一致，FIFO 模式不发送旧 batch_id。

### 9.4 响应式与可访问性

必须在真实浏览器或 Android WebView 检查：

- 1440 × 900；
- 接近 768px 的窄桌面/平板；
- 390 × 844 移动视口。

每档至少覆盖：

- 首次加载、已有明细、零结果、目录分页失败、模板/批次加载失败；
- 编辑器打开/关闭、完成、Escape、遮罩关闭和 Android 原生返回；
- 未填写、阻塞、字段错误、服务端结构化错误和提交确认；
- 长物品名、长 SKU、混合单位、多明细和固定底部操作区。

量化检查包括：

- 页面无横向滚动；编辑器 clientWidth === scrollWidth；
- 编辑器、列表和固定操作区的 getBoundingClientRect() 坐标稳定；
- 移动端最后一条明细和最后一个字段能滚动到安全区上方；
- 字段标题、输入框和选择器的实际宽度/高度对齐；
- 关闭后焦点回到触发物品或搜索框；
- aria-label、aria-invalid、aria-busy 和错误播报完整；
- prefers-reduced-motion 下不依赖动画完成业务提交。

### 9.5 工程验证

- cd frontend; pnpm build
- 相关纯模型/状态测试（不新增不必要的测试依赖）
- 相关 core 定向测试或 HTTP smoke（仅在契约/权限受影响时扩大）
- git diff --check
- rg 检查删除的步骤状态、过时组件事件和旧文案无残留
- 浏览器控制台无新增 error、warning 或 accessibility issue

## 10. 风险与控制

| 风险                                  | 控制措施                                                                                  |
| ------------------------------------- | ----------------------------------------------------------------------------------------- |
| 用户想快速连续添加多个物品            | 完成明细后提供“完成并继续添加”；未来可增加显式默认值/应用到后续明细，不恢复隐式批量填充。 |
| 新物品尚未配置就离开                  | 保留不完整本地明细并显示待配置；提交时定位首错，删除是明确动作。                          |
| 入库编辑器字段过长                    | 使用分组、内容区滚动和稳定底部操作，不拆成第二个业务步骤；移动端使用通用底部面板。        |
| 模板/批次异步响应覆盖用户输入         | 继续使用每条明细请求版本、取消控制器和“用户选择优先”规则。                                |
| 目录误触导致已配置明细被删除          | 取消目录 toggle 移除，移除只在复核列表提供。                                              |
| 旧草稿无法恢复                        | 保持现有版本和字段，活动编辑器不持久化；真正改变序列化结构时增加显式迁移。                |
| 过度抽象导致入库/出库业务分支难以维护 | 只共享目录、身份头部和布局原语，模板/批次/审批规则仍由领域组件拥有。                      |

## 11. 非目标

- 不新增服务端库存预占、拆批次、批次锁定或提交前库存承诺。
- 不把入库模板字段复制到物品主数据，也不在出库新增客户、价格或销售结算字段。
- 不改入库/出库审批工作台的列表、权限和库存事务。
- 不新增 Server、Android 或 Desktop 原生设置 UI。
- 不通过 Shell Bridge 代理业务 API，不在前端直接调用 Rust 内部函数。
- 不因为本次 UI 改造引入新的前端框架、状态管理库或第三方表单库。

## 12. 完成定义（本轮已满足）

当且仅当以下条件全部满足，才可把本整改标记为完成：

2. 入库和出库的每条明细字段在一个连续编辑会话中完成，复核列表不再成为第二套编辑表单。

5. 三档视口、Android 原生返回、键盘焦点、异步失败和结构化后端错误均通过验收。
6. 代码、页面文档、路由说明、原生返回记录和代码地图不再描述已删除的两步工作流。
