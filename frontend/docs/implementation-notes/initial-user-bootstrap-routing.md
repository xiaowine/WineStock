# 首用户初始化与登录入口分流实施方案

> 文档状态：实施基线。用于约束首用户状态接口、匿名认证入口、服务切换失效策略和验收范围；实际完成情况以代码、测试和最终验收记录为准。

## 1. 背景与目标

当前认证入口默认展示登录页，无法区分“服务尚未创建任何用户”和“服务已有用户但当前未登录”两种状态。首次部署时，用户需要自行发现注册入口；正常运行时，注册入口又容易被误认为是开放注册。

本方案将“是否需要创建首个用户”变成服务端提供的明确状态，并由前端统一认证入口根据该状态选择登录或首用户注册页面。

目标：

- 首次初始化时自动进入首用户注册流程。
- 已存在用户时默认进入登录流程。
- 不在登录页和注册页之间短暂闪烁错误页面。
- 注册成功后继续复用现有会话恢复和默认业务路由逻辑。
- 服务端保证首用户创建的原子性，避免并发初始化产生多个首用户。
- 运行设置切换服务后，不复用旧服务的初始化判断。

非目标：

- 不新增普通用户自助注册能力。
- 不把用户数量或用户名暴露给未鉴权客户端。
- 不改变现有登录、刷新、登出和权限接口的业务语义。
- 不让前端判断替代后端的注册授权和事务校验。

## 2. 组件边界

```text
frontend -> GET /api/auth/bootstrap-status
frontend -> POST /api/auth/register
frontend -> POST /api/auth/login
core     -> 公开初始化状态、注册事务和认证 API
shared   -> 不新增用户业务状态
server   -> 不复制判断逻辑，仅启动 core
```

- `core` 拥有首用户状态的权威来源、公开状态接口、注册并发保护和稳定错误码。
- `frontend` 拥有认证入口状态机、路由分流、加载/错误/恢复呈现和服务地址变化后的状态失效。
- `server`、Android 和未来 Desktop shell 不实现用户判断，也不增加平台专用注册 UI。

## 3. 服务端契约

### 3.1 初始化状态接口

新增无需鉴权的接口：

```http
GET /api/auth/bootstrap-status
Accept: application/json
```

成功响应：

```json
{
  "requires_initial_user": true
}
```

字段约束：

- `requires_initial_user` 必须是布尔值。
- `true` 表示当前服务没有可用用户，客户端应进入首用户注册。
- `false` 表示至少已有一个用户，客户端应进入登录。
- 不返回用户数量、首用户名称、用户 ID 或权限明细。

推荐 OpenAPI 标识：`AuthBootstrapStatus`。

### 3.2 错误契约

首用户注册接口在事务提交前再次确认用户表状态。已有用户时返回稳定业务错误：

```json
{
  "code": "initial_user_already_exists",
  "message": "首个用户已经创建"
}
```

前端将该错误映射为“首个账户已创建，请使用登录”，并跳转登录页；不得把它显示为泛化的“请求无效”。

状态接口的异常遵循现有 API 错误包装，不根据 401 判断初始化状态。该接口不应返回 401；服务不可用、数据库错误或响应结构错误分别由前端显示为连接错误、服务错误或契约错误。

### 3.3 并发与事务

首用户注册必须在 core 的注册 service/repository 边界内完成：

1. 开启数据库事务。
2. 在事务中读取用户是否存在。
3. 只有用户表为空时才创建首用户，并赋予初始化管理员权限。
4. 提交事务。
5. 用户已存在或唯一约束冲突时回滚并返回 `initial_user_already_exists`。

状态查询只用于界面分流，不能作为创建权限。两个客户端同时打开注册页时，最多一个请求可以成功。

### 3.4 OpenAPI 与验证

实施前先更新并核对 `/api-docs/openapi.json`：

- 新增 `GET /api/auth/bootstrap-status`。
- 明确 200 响应 schema。
- 明确注册接口的首用户冲突错误。
- 为状态接口增加 core controller/service 测试和 OpenAPI 契约测试。

## 4. 前端状态机

认证入口新增独立的 `AuthEntryState`，建议状态如下：

```ts
type AuthEntryState =
  | { kind: "checking" }
  | { kind: "needs-initial-user" }
  | { kind: "login" }
  | { kind: "error"; message: string };
```

状态转换：

```text
进入 /auth
  -> checking
  -> requires_initial_user=true  -> /register
  -> requires_initial_user=false -> /login
  -> 网络/响应错误             -> error
```

要求：

- `checking` 阶段保持认证页稳定骨架，不先渲染登录表单。
- 查询成功后才挂载 LoginPage 或 RegisterPage，避免登录/注册闪烁。
- 已认证用户访问 `/auth` 时直接进入默认业务路由，不重复查询并显示认证页面。
- `requiresService = false` 的运行设置页不受该状态机阻塞。
- API 地址改变后清理旧状态并重新进入 `checking`，禁止复用旧服务的结果。

## 5. 路由设计

建议增加认证入口路由：

```text
/auth       -> AuthEntryPage
/login      -> LoginPage
/register   -> RegisterPage
```

### 5.1 `/auth`

- `requiresAuth = false`。
- `requiresService = true`。
- 保存 `returnTo`，通过合法内部路径校验后传递给登录或注册页。
- 负责调用 bootstrap status 和跳转，不拥有登录或注册表单。
- 已认证状态直接跳转默认应用路由。

### 5.2 `/login`

- 进入时若 bootstrap 状态为 `needs_initial_user`，重定向 `/register`。
- 不在页面内展示普通注册按钮。
- 保留运行设置入口和现有错误恢复行为。

### 5.3 `/register`

- 进入时若状态为 `login`，重定向 `/login`。
- `needs_initial_user` 时标题改为“创建管理员账户”，提交按钮为“创建账户”。
- 首用户成功后复用现有自动登录和默认路由逻辑。
- 已有用户时不显示注册表单，避免用户误以为支持开放注册。

### 5.4 路由守卫顺序

建议顺序：

1. 读取服务无关运行设置路由并直接放行。
2. 检查 API 地址和服务可用性。
3. 对 `/auth`、`/login`、`/register` 执行 bootstrap 状态分流。
4. 再执行匿名/已认证、强制改密和 `returnTo` 安全校验。
5. 业务路由继续执行现有权限守卫。

守卫不能通过调用注册接口来探测状态，也不能将任意非 2xx 登录错误解释为“没有用户”。

## 6. API client 与缓存

在 `frontend/src/api/auth.ts` 增加 bootstrap 状态请求，职责仅包括：

- 请求状态接口。
- 校验响应为布尔字段。
- 将网络、HTTP 和结构错误映射为稳定前端错误。

新增会话级内存缓存，按实际 API 根地址隔离：

```ts
type BootstrapStatus = {
  apiBaseUrl: string;
  requiresInitialUser: boolean;
  checkedAt: number;
};
```

缓存规则：

- 只保存在内存，不写入 `localStorage`。
- API 地址、运行模式或 Shell 快照变化时失效。
- 首用户注册成功后立即更新为 `false`。
- 登出不需要重新查询，因为用户是否存在没有改变。
- 页面重新加载可以重新查询；查询成本低于错误地展示错误入口。

## 7. 页面交互与文案

### 首次初始化

- 页标题：“创建管理员账户”。
- 辅助文案：“这是此 WineStock 服务的第一个账户。”
- 只显示用户名、密码、确认密码和创建按钮。
- 不显示“已有账户？登录”链接，避免首次初始化产生无效分支。

### 已有用户

- 页标题：“登录 WineStock”。
- 注册入口不作为普通按钮展示。
- 可保留“运行设置”入口，便于地址错误时恢复。

### 状态查询失败

- 标题：“无法确认账户状态”。
- 说明当前服务可能尚未启动、地址不可达或响应无效。
- 提供“重试”和“运行设置”两个动作。
- 不默认进入登录，也不默认开放注册。

### 注册竞态

- 注册提交返回 `initial_user_already_exists`：提示“首个账户已创建，请使用登录”，然后进入登录。
- 注册提交网络失败：保留表单草稿，不清除密码字段以外的安全可保留内容。
- 注册成功：显示现有成功 Notice，再进入默认业务页面。

## 8. 安全边界

- bootstrap status 是公开接口，只返回是否需要首用户，不返回用户资料。
- 首用户注册不是由前端隐藏或显示决定，core 必须在服务端强制执行。
- 首用户密码继续使用现有密码策略和哈希流程。
- 错误消息不得包含数据库细节、用户名枚举或 SQL/唯一约束信息。
- `returnTo` 只能接受站内绝对路径，拒绝协议、双斜杠、反斜杠和外部地址。
- 远端服务切换后不得把旧服务的 `requiresInitialUser` 用于新地址。

## 9. 实施步骤

### 阶段一：core 契约

- 增加 bootstrap status DTO、controller、service 方法和 OpenAPI。
- 增加首用户注册事务内的二次检查和稳定错误码。
- 添加空用户、已有用户、并发注册和数据库异常测试。
- 用 `/api-docs/openapi.json` 核对实际契约。

### 阶段二：frontend 状态与路由

- 增加 API client、响应校验和按 API 根地址隔离的内存缓存。
- 增加 `AuthEntryPage` 与 `/auth` 路由。
- 调整认证守卫分流顺序。
- 将登录页、注册页的相互跳转改为状态驱动。
- 接入 API 地址变化、注册成功和 Shell 初始化失效。

### 阶段三：页面与文案

- 实现 checking、error、needs-initial-user、login 四种稳定呈现。
- 调整首用户注册标题、说明和成功路径。
- 验证无服务、远程服务、已有用户和首次初始化状态。

### 阶段四：清理与文档

- 删除依赖“登录失败后提示注册”的旧兼容逻辑。
- 删除普通登录页上的开放注册入口（如果产品不要求开放注册）。
- 更新 `frontend/docs/routes.md`、前端代码地图和认证页面文档。
- 更新 core API 文档和权限/初始化说明。

## 10. 测试矩阵

### Core

- 空用户表：状态接口返回 `true`。
- 已有用户：状态接口返回 `false`。
- 状态接口不需要 token。
- 首用户注册成功后状态变为 `false`。
- 已有用户注册返回 `initial_user_already_exists`。
- 两个并发首用户注册只有一个成功。
- 数据库失败不会返回“需要注册”。

### Frontend

- 首次打开 `/auth` 不闪现登录页，最终进入注册页。
- 已有用户进入登录页，不显示普通注册入口。
- 手动访问 `/login` 或 `/register` 时按状态重定向。
- 状态请求失败显示重试和运行设置，不进入错误的默认分支。
- 注册竞态错误自动转登录并保留明确提示。
- API 地址切换后重新查询，不复用旧服务状态。
- `returnTo` 只恢复合法站内路径。
- 1440×900、接近 768px、390×844 均无横向溢出。
- 浏览器控制台无新增错误或 Vue 警告。

### Shell/平台

- 本机服务尚未启动时仍能进入运行设置。
- 本机服务启动后首次打开 `/auth` 正确分流。
- Android/桌面 WebView 与普通 Web fallback 使用相同分流逻辑。
- 远程 API 地址切换后前端状态、会话和 bootstrap 缓存同步清理。

## 11. 验收标准

交付必须满足：

- 空用户服务启动后，用户无需寻找入口即可看到首用户注册页。
- 已有用户服务不会默认展示首用户注册流程。
- 页面在状态查询期间不闪烁登录/注册表单。
- 后端并发注册不会创建多个首用户。
- 服务地址切换不会污染认证入口判断。
- 运行设置、登录、注册和业务页面的现有错误恢复行为不回退。
- `pnpm build`、core 最窄测试、`git diff --check` 和三档浏览器视口检查通过。

## 12. 风险与决策

| 风险                     | 处理决定                                         |
| ------------------------ | ------------------------------------------------ |
| 状态接口被误认为安全边界 | 注册 service 内再次检查并用事务保证原子性        |
| 查询失败时错误开放注册   | 失败状态只显示重试，不默认注册                   |
| 多服务地址复用旧状态     | 以内存 API 地址作为缓存隔离键，地址变化立即失效  |
| 旧客户端不认识新错误码   | 保留通用错误 fallback，新客户端优先识别稳定 code |
| 首用户注册后返回登录页   | 首用户成功沿用现有自动登录，不增加二次登录步骤   |
| 普通用户需要邀请注册     | 后续另建受权限控制的邀请流程，不复用首用户接口   |
