# 物品目录结构化筛选实施方案

本文记录物品目录结构化筛选的跨 `core` 与 `frontend` 实施方案。
目标是在保留现有关键词搜索、库存状态筛选、排序和分页行为的基础上，接入分类、属性模板、计量单位、库位和可搜索模板属性筛选。

本文是实施说明，不替代 `core/docs/business-api/items.md`、`frontend/docs/ui-design-guidelines.md` 和 OpenAPI 契约。实现完成后必须把最终行为同步回规范文档和代码地图。

## 实施状态

已完成。最终实现覆盖 `core` 与 `frontend`，并已同步业务 API 文档和代码地图。

落地行为与本文方案一致，补充说明如下：

- 前端打开高级筛选 Dialog 时，按当前已应用的关键词、库存状态和结构化筛选请求一次候选值；修改 Dialog 草稿期间不连续刷新候选值，避免草稿操作触发请求抖动。
- 服务端按分面语义计算候选值；前端把服务端暂时未返回的已选值合并为“不可用”项，用户重新应用前不会被静默删除。
- “清除筛选”空状态操作会同时清除关键词、库存状态和高级筛选；Dialog 内“清除全部”只清除草稿，必须点击“应用筛选”才改变目录。
- 动态字段按基础字段和模板属性的返回顺序连续展示；当前未额外增加只承担视觉分组作用的标题。

## 实施前状态

当前运行服务已经提供：

- `GET /api/items`
  - 分页。
  - 关键词搜索。
  - `category_id` 分类筛选。
  - `attribute_template_id` 属性模板筛选。
  - `stock_filter` 库存状态筛选。
  - 服务端排序。
- `GET /api/items/filter-values`
  - 返回基础筛选字段。
  - 返回模板中标记为 `searchable = true` 的属性及其候选值。
  - 返回候选值对应的去重物品数量。

当前前端物品页面只接入：

- 关键词搜索。
- 库存状态筛选。
- 排序。

尚未接入：

- 分类筛选。
- 属性模板筛选。
- 筛选值接口。
- 计量单位筛选。
- 库位筛选。
- 可搜索模板属性的精确筛选。

当前后端也存在一个契约缺口：`filter-values` 能返回单位、库位和模板属性候选值，但 `GET /api/items` 没有接收这些动态字段筛选条件的查询参数。因此完整实现不能只修改前端。

## 目标

完成后，用户可以组合使用：

- 关键词搜索。
- 分类。
- 属性模板。
- 库存状态。
- 计量单位。
- 当前有库存的库位。
- 模板中允许搜索的物品属性。
- 排序。

筛选必须由服务端执行，前端不能只筛选当前已加载页。

筛选状态变化后必须：

- 取消旧请求。
- 从第一页重新查询。
- 保留稳定的工具栏和旧结果，直到新结果成功返回。
- 刷新、分页和排序继续携带当前筛选条件。
- 与服务端返回的总数、状态计数和分页保持一致。

## 非目标

本轮不实现：

- 保存个人筛选方案。
- 多套筛选预设。
- 任意表达式、括号和 NOT 条件。
- 模糊匹配动态属性值。
- 对图片属性按图片内容筛选。
- 让物品私有自定义属性进入结构化筛选。
- 在前端自行推导候选值或命中数量。

关键词搜索仍可以匹配自定义属性名称和值。

## 所有权

### `core`

负责：

- 公共查询契约。
- 筛选参数校验。
- 动态筛选 SQL。
- 候选值和计数聚合。
- 权限和错误响应。
- OpenAPI。

### `frontend`

负责：

- 筛选值 API client。
- 已应用筛选和面板草稿状态。
- 筛选面板、工具栏入口和激活数量。
- 请求取消、分页重建和错误反馈。
- 桌面与移动端响应式呈现。

前端不得复制后端筛选语义，也不得从当前目录结果反向生成候选值。

## 筛选语义

统一采用以下逻辑：

- 同一字段选择多个值：OR。
- 不同字段之间：AND。
- 结构化筛选与关键词、分类、模板和库存状态之间：AND。
- 没有选择值的字段不进入请求。

示例：

```text
计量单位：个、盒
库位：A01
品牌：Murata、TDK
```

等价于：

```text
(计量单位 = 个 OR 计量单位 = 盒)
AND 库位 = A01
AND (品牌 = Murata OR 品牌 = TDK)
```

模板属性使用保存后的类型化值进行精确匹配。数字、日期、布尔值和单位必须沿用后端已有的规范化规则，不能由前端生成另一套字符串格式。

## 字段 key

基础字段使用稳定 key：

```text
base:unit
base:location
```

分类和属性模板已经拥有稳定 ID，继续使用独立的 `category_id` 和 `attribute_template_id`，不重复进入动态 `filters`。

模板属性不得继续使用可能重名或改名的 `template:<字段名>` 作为筛选标识。实现前应改成：

```text
template:<definition_id>
```

`label` 继续返回用户可见字段名。这样字段改名不会破坏已应用条件，不同模板中的同名字段也不会发生冲突。

由于前端尚未消费当前动态 key，本次可以直接进行破坏性调整，不增加旧 key 兼容层。

## 列表查询契约

保留 `GET /api/items`，增加可选查询参数 `filters`。

`filters` 使用 URL 编码后的 JSON 数组：

```json
[
  { "key": "base:unit", "values": ["个", "盒"] },
  { "key": "base:location", "values": ["A01"] },
  { "key": "template:42", "values": ["Murata", "TDK"] }
]
```

完整请求示例：

```text
GET /api/items?page=1&page_size=50&category_id=3&stock_filter=all&sort=name&filters=<url-encoded-json>
```

选择 JSON 字符串而不是引入新的查询解析库，原因是：

- 字段 key 和值可以安全包含中文、冒号和空格。
- 同一字段多值结构明确。
- 前后端均可复用现有 JSON 序列化能力。
- 不需要维护自定义分隔符和转义规则。

限制：

- `filters` 解码后最大 `4096` 字节。
- 最多 `12` 个字段。
- 每个字段最多 `20` 个值。
- 单个值去除首尾空白后长度为 `1..=256`。
- 相同 key 合并并去重。
- 空数组视为未筛选。
- 未知基础 key、无效模板定义 ID、不可搜索定义和类型不匹配均返回 `400 invalid_request`。

后端 controller 负责解析和基础校验，service 负责确认模板定义存在且 `searchable = true`，repository 只接收已经规范化的筛选条件。

## 筛选值接口

扩展 `GET /api/items/filter-values`，使其接受与目录一致的上下文：

- `search`
- `category_id`
- `attribute_template_id`
- `stock_filter`
- `filters`

候选值计数采用分面筛选语义：

- 计算某字段候选值时，应用搜索、固定筛选和其它字段条件。
- 暂时排除该字段自身的已选值。
- 当前已选值即使命中数量为 `0`，响应中也必须保留或由前端与已应用状态合并保留。

例如已经选择“品牌 = TDK”时，品牌候选值仍可展示 Murata、TDK 等在其它条件下可用的值；单位和库位计数则必须受到品牌条件影响。

筛选值范围应与物品目录一致，不再固定只统计仍有库存的物品。库存范围由 `stock_filter` 决定：

- `all` 包含零库存和有库存物品。
- `out_of_stock` 只包含零库存物品。
- 其它状态按现有库存状态语义处理。

库位只对仍有余额的批次产生值，因此零库存物品不会贡献库位候选值。

## Repository 实现

不要把动态值直接拼接进 SQL。

建议流程：

1. 先建立物品基础候选集合，应用软删除、关键词、分类、模板和库存状态。
2. 对每个动态字段增加参数化 `EXISTS` 条件。
3. 同字段多值在同一个 `EXISTS` 中使用参数化 `IN` 或等价 OR。
4. 不同字段使用多个 `EXISTS`，自然形成 AND。
5. 库位筛选只匹配 `remaining_quantity > 0` 的批次。
6. 模板属性通过 `definition_id`、规范化值和实际单位匹配。

必须继续使用绑定参数，不允许把 key、definition ID 或值直接插入 SQL 文本。只有经过枚举匹配的基础字段可以选择预定义 SQL 片段。

状态计数继续忽略当前 `stock_filter`，但必须应用搜索、分类、模板和动态筛选条件，使“全部、需处理、缺货、待补货、需配置”的数量与当前其它条件一致。

## 前端状态

新增物品目录筛选 composable，或在 `ItemsPage` 拆分达到相同职责边界。

至少区分：

```text
appliedFilters  已应用到目录请求的筛选
draftFilters    当前筛选面板中尚未应用的草稿
filterFields    服务端返回的候选字段和值
filterPending   筛选值加载状态
filterError     筛选值加载错误
```

交互规则：

- 打开面板时从 `appliedFilters` 复制草稿。
- 修改草稿不请求物品目录。
- 点击取消直接丢弃草稿。
- 点击应用后替换已应用筛选、取消旧目录请求并查询第一页。
- 点击清除全部只清理草稿，仍需点击应用才影响目录。
- 目录刷新和分页继续使用 `appliedFilters`。
- 服务端不再返回某个已选值时，不得静默清除；至少保留到用户再次应用，并标记为当前不可用。

关键词、库存状态和排序继续保持即时应用，不进入高级筛选草稿。

## 工具栏

保持现有工具栏顺序：

```text
搜索 | 库存筛选 | 排序 | 高级筛选 | 刷新 | 列表展示设置 | 新建
```

高级筛选使用统一线性图标按钮，并提供：

- `title="高级筛选"`
- `aria-label="高级筛选"`
- 已应用字段数量徽标或等价紧凑提示。

激活数量按字段计数，不按选择值数量计数。例如单位选择两个值、品牌选择三个值，显示为 `2` 个已启用筛选。

动态数量不能改变按钮尺寸或推动其它工具栏控件。

## 筛选面板

筛选属于临时操作，使用共享 `ModalDialog`：

- 桌面使用紧凑 Dialog。
- 移动端由共享 Dialog 响应式切换为底部或全屏面板。
- 不维护两套业务状态。

面板顺序：

```text
分类
属性模板
基础筛选
  计量单位
  库位
模板属性筛选
底部操作
  清除全部 | 取消 | 应用筛选
```

分类和属性模板使用 `SelectControl`。

动态字段允许多选，不能用单选选择框。每个字段使用：

- 字段标题。
- 值列表。
- 值名称和命中数量。
- 选中背景和原生 checkbox 语义。
- 候选值过多时的字段内搜索或折叠。

第一阶段每个字段最多直接展示前 `8` 个值，其余通过“显示更多”展开。不得让一个高基数字段无限推高整个 Dialog。

文件类型字段不进入筛选面板。`mixed` 字段按文本值显示。布尔值转换为“是/否”，但请求仍发送后端返回的原始字符串值。

## 列表状态

应用筛选后：

- 空结果显示“没有符合条件的物品”。
- 提供“清除筛选”。
- 清除操作同时清除关键词、库存状态和高级筛选时，文案必须明确；如果只清除高级筛选，应使用“清除高级筛选”。
- 后台刷新保留旧结果和滚动上下文。
- 分页只追加当前筛选上下文中的下一页。
- 筛选变化后不能继续追加旧筛选的分页结果。

保存物品并刷新目录时继续使用当前已应用筛选。如果保存后该物品不再满足筛选条件，允许它从成功刷新后的结果中消失，不保留前端兼容项。

## 权限和错误

- 列表和筛选值接口统一要求 `stock.item.read`。
- 前端不因为缺少模板管理权限而隐藏属性筛选；读取和管理权限不同。
- `400` 表示筛选参数无效，前端保留旧结果并提示筛选条件需要重新选择。
- `401`、`403` 和网络错误继续使用统一 API client 与服务可用性处理。
- 筛选值加载失败不应阻断已有目录浏览；面板显示错误和重试入口。
