# 代码地图粒度收敛方案

本方案把代码地图从“逐文件 1:1 镜像”收敛为“模块/职责边界”粒度，降低维护成本并消除已出现的漂移。
它只改 `docs/` 与流程规则，不改任何源码；代码地图体系本身保留，不废除。

## 背景与问题

- `docs/code-map/frontend.md` 已达 251 行，绝大部分条目是单个文件的行为描述，与源码形成 1:1 镜像关系；`core` 子地图也存在同样趋势。
- 逐文件镜像的维护责任压在每一次改动上，天然会烂。已观察到漂移证据：`frontend.md` 的文档段落把 `inbound-template-usability-remediation.md` 重复列出两次（第 234、237 行）。
- 关键冗余：`docs/agent-checklist.md` 的 Comment Check 已强制要求**每个源码文件以中文文件头注释开头，说明职责、所属层和边界**。文件级地图条目是同一信息的第二份拷贝——收敛粒度不损失信息，只是删除会漂移的副本。

## 目标与非目标

目标：

- 地图只回答“这块能力归谁所有、边界在哪、依赖方向如何”，用模块/目录/领域作为条目单位。
- 每份子地图有明确行数预算，逐文件细节由文件头注释和组件 `docs/` 承担。
- 修正现有漂移，并调整流程规则使收敛后的粒度可持续。

非目标：

- 不废除代码地图或改变“中文编写”“同改动内更新”的既有纪律。
- 不迁移或重写组件 `docs/` 下的设计文档；只调整地图对它们的引用方式。
- 不引入自动生成工具；收敛后的粒度应当低频变化，人工维护成本可接受。

## 新粒度约定

写入 `docs/code-map.md` 总索引，作为全部子地图的权威约定：

1. **条目单位是模块/目录/领域，不是文件。** 一个条目覆盖一组内聚文件（如 `frontend/src/auth/` 整体描述会话模型与边界），而不是逐文件各写一行。
2. **每个条目只记录三件事：** 拥有的职责；明确不拥有的边界；依赖方向或被谁使用。不复述文件内部行为细节、交互流程或验收规则——那些属于文件头注释和组件 `docs/`。
3. **仍可点名单个文件的例外情形：**
   - 公共入口点（`lib.rs`、`main.ts`、bootstrap、路由装配）；
   - 跨组件契约（如 `frontend/src/shell/contract.ts`）；
   - 机制不寻常、无法从目录结构推断所有权的文件（如 core 通过 `#[path]` 挂载 `src/tests/` 的测试布局）。
4. **行数预算：** 每份子地图目标 ≤ 100 行；超出预算视为粒度失控信号，应先合并条目而不是继续追加。
5. **文档清单单一来源：** 各组件 `docs/` 下的设计文档清单（`page-*.md`、implementation-notes 等）由组件自己的 `docs/README.md` 索引维护；地图只链接该索引一次，不再复制文档列表。本次观察到的重复条目正是复制清单导致的。

## 实施步骤

按子地图逐份整改，每份地图在**一个改动内整体重写**，不留新旧粒度混杂的中间态：

1. **立即修复：** 删除 `frontend.md` 第 237 行的重复条目（与整改可合并进行）。
2. **`frontend.md`（251 行，收益最大）：** 重组为 工程入口 / 路由与导航 / Shell 与鉴权会话 / API 层 / 全局反馈与可用性 / 业务页面域（按领域分组：物品、出入库、审批、模板、库位、替代料、用户、审计、看板）/ 共享组件域 / 样式体系 几个分组条目；“样式和文档”一节的文档清单整体移交 `frontend/docs/README.md` 索引。整改时逐条核对现状，顺带清除其余漂移。
3. **`core/stock.md`、`core/http-auth-users.md`、`core/persistence.md`：** controller/service/repository 逐文件条目合并为子域条目（物品、模板、库位、出入库、审批、替代料、看板、审计），保留错误收敛、分页、投影等横切文件的点名。`core/http-api.md` 是路径清单不是文件镜像，保留现状。
4. **`workspace.md`（121 行）：** 按预算内审视，重点确认测试布局、验证入口等“机制不寻常”内容保留，纯目录复述合并。
5. **`android.md`（195 行）：** 与 `frontend.md` 同性质的逐文件镜像，按 工程与构建 / Activity 与 Application 级 core / WebView 环境 / Shell Bridge 传输 分组收敛；启动流程图和边界一节信息密度高，保留。
6. **`shared.md`、`server.md`（45–46 行）：** 已在预算内且条目即模块（小 crate 文件=模块），仅按新约定核对条目三要素，预计不改或小改。
7. **规则文本同步（同批完成）：**
   - `docs/code-map.md`：新增“粒度约定”一节（即上文五条）。
   - `docs/agent-checklist.md` Code Map Check：更新触发条件——**模块/领域的职责、边界或依赖方向变化时**更新地图；在既有模块内新增文件、且文件头注释已说明职责的，不再要求地图条目。
   - `AGENTS.md` 实施规则中“更新代码地图”的表述指向新粒度约定。

步骤 2–5 可分多次提交，但每份地图内部必须一次到位。

## 风险与缓解

- **丢失文件级检索入口：** 依赖地图定位具体文件的工作流改为“地图定位模块 → Glob/文件头注释定位文件”。Comment Check 保证每个文件自带职责说明，入口点例外规则保证关键文件仍被点名。
- **整改本身引入新漂移：** 每份地图重写时逐条与当前源码目录核对，视为一次地图审计；发现的其它不一致按 checklist“先修正地图”规则一并处理。
- **粒度约定被逐渐突破：** 行数预算提供客观信号；评审时超预算的地图改动应先质疑粒度而不是内容。

## 验收标准

- 每份子地图 ≤ 100 行（`http-api.md` 路径清单除外）；不存在对同一目录下多个同类文件的逐条镜像描述。
- `frontend.md` 重复条目消除；组件文档清单只存在于组件 `docs/README.md`，地图仅链接索引。
- `docs/code-map.md` 含粒度约定；`agent-checklist.md` 与 `AGENTS.md` 的更新触发条件与之一致。
- 所有地图内部链接有效；条目描述与当前源码目录抽样核对无漂移。
